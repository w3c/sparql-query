6Recommendations for the specification

Ordered by the gap each one closes. R-1 through R-3 are the substantive ones.

R-1State that imposing resource limits and refusing queries is conforming behaviour

Gap. Per §1.4, the only refusal licence in the document is dataset-shaped. conformance addresses query strings, results and media type, and says nothing about a service declining or aborting work. Every mitigation in §3.B therefore has no conformance cover, and an implementer can reasonably read the spec as requiring unbounded effort on any syntactically valid query.

Recommendation. Add to security, with a cross-reference from conformance, language to the effect that: SPARQL defines the results of a query, not the resources required to produce them; several constructs — notably unbounded property paths, nested OPTIONAL, EXISTS, aggregation and regular-expression matching — permit short queries whose evaluation cost grows superlinearly in the data or the query; a service MAY impose implementation-defined limits on query complexity, evaluation time, memory, intermediate and final result size, nesting depth, and string and numeric magnitude, and MAY refuse or abort a request that exceeds them; and a service that does so remains conforming.

The last clause is the point: without it, hardening looks like non-conformance.

R-2Draft the privacy section (currently TODO)

Candidate content, each item traced to a threat above.

  1. Query text is sensitive. Queries carry the selectors — identifiers, locations, contact details. They accumulate in logs, URLs, Referer headers and shared links, which are rarely classified at the sensitivity of the data they select over. Prefer POST; classify, redact and set retention on query logs. (SQ-CONF-07)
  2. Dereference discloses interest to third parties. FROM, FROM NAMED and SERVICE reveal to an external party which graphs a requester is interested in. (SQ-CONF-07, SQ-NET-03)
  3. Hashing is not de-identification. An unsalted hash of a low-entropy identifier — email, phone number, national id — is reversible by enumeration; providing MD5/SHA1/SHA2 does not make such a construction anonymizing. (SQ-CONF-06)
  4. Aggregate-only exposure is not anonymity. Differencing over COUNT recovers individual facts. (SQ-CONF-08)
  5. Joining enables re-identification, and federation does it across administrative and jurisdictional boundaries as a side effect of evaluation. (SQ-CONF-08)
  6. Metadata is data. Graph names and predicate vocabularies are enumerable in one query and commonly encode tenant, customer and case identifiers. (SQ-CONF-02)
  7. Blank node labels should not be correlatable across result sets, since the language's scoping rules permit — but do not require — opaque per-result-set labels. (SQ-CONF-05)

R-3Extend the security section

The section is inherited largely unchanged from SPARQL 1.1 and predates SERVICE being in this grammar, triple terms, and the escape-processing change. Suggested additions, with the existing dereference, file:, extension and confusables paragraphs retained.

R-4Smaller, optional notes

  • propertypath-arbitrary-length — a non-normative note that termination is guaranteed but cost is not, and that evaluation may be quadratic in graph size when both endpoints are unbound. The section currently reassures on termination, which could be read as reassurance about cost.
  • func-regex — a note that the pattern may be a variable and that backtracking implementations of fn:matches have exponential worst cases; implementations are encouraged to use a linear-time matcher. Worth WG discussion, since back-references in the XPath 3.1 regex language may be unimplementable in such a matcher — a genuine conformance-versus-safety tension.
  • modOrderBy — note that because the ordering is partial, consumers must not rely on result byte-equality for integrity checks without canonicalizing.
  • syntaxVersionAnnouncement — note that a VERSION declaration is an author's announcement, not a verified property of the query, so processors should not gate on it for security purposes.
  • extensionFunctions — the error-case extension licence is appropriate for interoperability, but worth a note that it means "this expression raises an error" is not a portable property, which affects anything built on error behaviour.
