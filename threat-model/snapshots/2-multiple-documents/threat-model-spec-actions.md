# Threat Model: Specification Actions — SPARQL 1.2 Query Language

**Subject:** `spec/index.html` — SPARQL 1.2 Query Language, Editor's Draft
**Reviewed at:** commit `7f707ff` (2026-10-01)
**Status:** Not a W3C publication; carries no normative weight; does not represent Working Group consensus.

Changes to the SPARQL 1.2 Query Language Editor's Draft that the threat analysis would justify. The threats themselves — their mechanisms, impact and severity — are described in the companion [threat model](threat-model.md), whose threat identifiers (`SQ-NET-03` and so on) are used here without restating them.

Ordered by the gap each one closes. R-1 through R-3 are the substantive ones.

Section references are given as stable fragment ids from the specification (e.g. [`#specifyingDataset`](../../../spec/index.html#specifyingDataset)), because the published section *numbers* are generated by ReSpec and move as the draft changes.

---

## 1. R-1 — State that imposing resource limits and refusing queries is conforming behaviour

**Gap.** the threat model §1.4: the only refusal licence in the document is dataset-shaped. [`#conformance`](../../../spec/index.html#conformance) addresses query strings, results, and media type, and says nothing about a service declining or aborting work. Every mitigation in the threat model §3.B therefore has no conformance cover, and an implementer can reasonably read the spec as requiring unbounded effort on any syntactically valid query.

**Recommendation.** Add to [`#security`](../../../spec/index.html#security), and consider a cross-reference from [`#conformance`](../../../spec/index.html#conformance), language to the effect that: SPARQL defines the results of a query, not the resources required to produce them; several constructs — notably unbounded property paths, nested `OPTIONAL`, `EXISTS`, aggregation, and regular-expression matching — permit short queries whose evaluation cost grows superlinearly in the data or the query; a service **MAY** impose implementation-defined limits on query complexity, evaluation time, memory, intermediate and final result size, nesting depth, and string and numeric magnitude, and **MAY** refuse or abort a request that exceeds them; and a service that does so remains conforming. The last clause is the point: without it, hardening looks like non-conformance.

## 2. R-2 — Draft the `#privacy` section (currently `TODO`)

Candidate content, each item traced to a threat above:

1. **Query text is sensitive.** Queries carry the selectors — identifiers, locations, contact details. They accumulate in logs, URLs, `Referer` headers, and shared links, which are rarely classified at the sensitivity of the data they select over. Prefer POST; classify, redact, and set retention on query logs. (SQ-CONF-07)
2. **Dereference discloses interest to third parties.** `FROM`, `FROM NAMED`, and `SERVICE` reveal to an external party which graphs a requester is interested in. (SQ-CONF-07, SQ-NET-03)
3. **Hashing is not de-identification.** An unsalted hash of a low-entropy identifier — email, phone number, national id — is reversible by enumeration; providing `MD5`/`SHA1`/`SHA2` does not make such a construction anonymizing. (SQ-CONF-06)
4. **Aggregate-only exposure is not anonymity.** Differencing over `COUNT` recovers individual facts. (SQ-CONF-08)
5. **Joining enables re-identification,** and federation does it across administrative and jurisdictional boundaries as a side effect of evaluation. (SQ-CONF-08)
6. **Metadata is data.** Graph names and predicate vocabularies are enumerable in one query and commonly encode tenant, customer, and case identifiers. (SQ-CONF-02)
7. **Blank node labels should not be correlatable** across result sets, since the language's scoping rules permit — but do not require — opaque per-result-set labels. (SQ-CONF-05)

## 3. R-3 — Extend `#security`

The section is inherited largely unchanged from SPARQL 1.1 and predates `SERVICE` being in this grammar, triple terms, and the escape-processing change. Suggested additions, with the existing dereference, `file:`, extension, and confusables paragraphs retained:

| Add | Substance | Threat |
| --- | --- | --- |
| **Resource limits** | Per R-1 | the threat model §3.B |
| **No access-control model** | The language defines no authorization; `GRAPH ?g` ranges over all named graphs in the active dataset; where dataset choice is a security boundary, set it in the protocol request and refuse in-query dataset descriptions — both explicitly permitted today | SQ-CONF-01 |
| **`SERVICE`** | Not mentioned at all, though `ServiceGraphPattern` is in this grammar. Note that the endpoint may be a **variable** bound at evaluation time, so static inspection of query text cannot allowlist it; that federated evaluation sends local bindings outward and so is an **exfiltration** channel independent of what the client is shown; and that `SILENT` suppresses errors from the client but should still be logged | SQ-NET-03 |
| **Exfiltration direction** | The current text covers inbound indirection only ("a source of indirection attacks"). Outbound data flow is the more severe case | SQ-NET-03 |
| **Scheme restriction** | Make the existing `file:` observation actionable: services dereferencing IRIs should restrict schemes and refuse loopback, link-local, and private address ranges, re-checking after redirects | SQ-NET-01/02 |
| **Query injection** | Applications constructing queries from untrusted input should use parameterized construction over string concatenation; if text must be built, escape per [`#sec-escapes`](../../../spec/index.html#sec-escapes). Note the comment-termination vector, since `#` comments end at U+000A or U+000D | SQ-INJ-01 |
| **Escape processing (a hardening)** | Processing escapes during parsing rather than before, with no rescanning of substituted output, removes an injection class present in SPARQL 1.1; excluding surrogates from numeric escapes removes an ill-formed-UTF-8 smuggling class. Implementations retaining a 1.1-era pre-parse pass are non-conforming **and** vulnerable | SQ-INJ-04 |
| **Nesting limits** | Grammar recursion is unbounded; limits should be applied after syntactic-sugar expansion, and in recursive term walkers as well as the parser | SQ-DOS-06/07 |
| **Blank node labels** | Should be opaque and scoped to one result set; deriving them from storage identifiers or from solution content leaks internal structure and enables cross-query correlation | SQ-CONF-05 |
| **`RAND`, `UUID`, `STRUUID`** | Not cryptographic; must not generate secrets, tokens, or capability identifiers. `UUID()`'s version being implementation-dependent means a conforming result may be predictable and host-identifying | SQ-INT-02 |
| **MD5 / SHA-1** | Legacy; unsuitable for security purposes. In-engine hashing also permits bulk guessing against values the requester cannot read | SQ-CONF-06 |
| **`DESCRIBE`** | Implementation-defined and unbounded; a neighbourhood walk can cross an authorization boundary in a way no pattern-level control can inspect | SQ-CONF-04 |
| **Extension functions** | Run with the engine's privileges. Function IRIs must not be resolved dynamically and must never be dereferenced; registration should be a privileged deployment-time action | SQ-EXT-01 |
| **Parser differentials** | A control that inspects query text can be desynchronized from the engine; enforce policy on the translated algebra. [`#whitespace`](../../../spec/index.html#whitespace)'s `?a<?b&&?c>?d` example is the cautionary case | SQ-INJ-03 |
| **Triple terms mention, not assert** | A triple term's presence is not an assertion, and a reifier's identity is not provenance. Relevant precisely because provenance is reification's main use | SQ-ID-03 |

## 4. R-4 — Smaller, optional notes

- **[`#propertypath-arbitrary-length`](../../../spec/index.html#propertypath-arbitrary-length)** — a non-normative note that termination is guaranteed but cost is not, and that evaluation may be quadratic in graph size when both endpoints are unbound. The section currently reassures on termination, which could be read as reassurance about cost.
- **[`#func-regex`](../../../spec/index.html#func-regex)** — a note that the pattern may be a variable and that backtracking implementations of `fn:matches` have exponential worst cases; implementations are encouraged to use a linear-time matcher. Worth WG discussion, since back-references in the XPath 3.1 regex language may be unimplementable in such a matcher — a genuine conformance-versus-safety tension.
- **[`#modOrderBy`](../../../spec/index.html#modOrderBy)** — note that because the ordering is partial, consumers must not rely on result byte-equality for integrity checks without canonicalizing.
- **[`#syntaxVersionAnnouncement`](../../../spec/index.html#syntaxVersionAnnouncement)** — note that a `VERSION` declaration is an author's announcement, not a verified property of the query, so processors should not gate on it for security purposes.
- **[`#extensionFunctions`](../../../spec/index.html#extensionFunctions)** — the error-case extension licence is appropriate for interoperability, but worth a note that it means "this expression raises an error" is not a portable property, which affects anything built on error behaviour.
