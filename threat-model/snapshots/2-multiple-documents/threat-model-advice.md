# Threat Model: Implementation Advice — SPARQL 1.2 Query Language

**Subject:** `spec/index.html` — SPARQL 1.2 Query Language, Editor's Draft
**Reviewed at:** commit `7f707ff` (2026-10-01)
**Status:** Not a W3C publication; carries no normative weight; does not represent Working Group consensus.

Countermeasures for the threats described in the companion [threat model](threat-model.md). That document says what can go wrong and how severely; this one says what to do about it. Threat identifiers (`SQ-NET-03` and so on) are shared between the two.

§1 gives the layered picture; §2 the per-threat detail; §3 what is left over once the countermeasures are in place. The appendices are working checklists.

Section references are given as stable fragment ids from the specification (e.g. [`#specifyingDataset`](../../../spec/index.html#specifyingDataset)), because the published section *numbers* are generated by ReSpec and move as the draft changes.

---

## 1. Defence architecture

Six layers, in evaluation order. The division matters: most failed deployments put the whole policy in layer 2, where parser differentials (SQ-INJ-03) defeat it.

**Layer 1 — Admission, before parsing.** Authenticate. Rate-limit in *work units*, not request counts (SQ-DOS-09). Cap request body size — as a coarse outer bound only, since expansion (SQ-DOS-07) makes it unsound as the real limit. Pin the method and content type; prefer POST so query text stays out of URLs and logs (SQ-CONF-07).

**Layer 2 — Parse and analyse, with the engine's own parser.** Select the grammar entry point from the protocol operation, never from the content (SQ-INJ-02). Enforce nesting-depth limits in the parser *and* in every recursive term walker (SQ-DOS-06). Apply AST and algebra size limits **after** sugar expansion (SQ-DOS-07). Feature-gate `SERVICE`, `FROM`/`FROM NAMED` dereference, `DESCRIBE`, and extension functions, on what the parse *contains* rather than on any `VERSION` declaration (SQ-INJ-05). Estimate cost and refuse above a threshold.

**Layer 3 — Authorize by constructing the dataset.** Set the dataset in the **protocol request** and refuse in-query dataset descriptions (SQ-CONF-01). The active dataset should contain exactly what the requester may see, so that protected triples never enter evaluation — this is what makes layer 4's inference channels (SQ-CONF-03) moot rather than merely narrower. Post-filtering results is a leak-rate reduction, not a confidentiality control.

**Layer 4 — Execute under enforced caps.** Wall-clock and memory limits enforced by the executor, not cooperatively. Bound *intermediate* cardinality, not just result size (SQ-DOS-01). Budget property-path expansion steps (SQ-DOS-02) and `EXISTS` inner evaluations (SQ-DOS-08). Cap string length, numeric digits and bit-length, group count, and accumulator size (SQ-DOS-03, SQ-DOS-04). Use a non-backtracking regex engine (SQ-DOS-05). Abort rather than truncate — silent truncation returns wrong answers. Enforce egress policy on the **resolved address** with redirects re-checked (SQ-NET-01, SQ-ID-02), from a distinct network identity with no ambient cloud credentials. Run least-privilege, with extension code inside the same caps (SQ-EXT-01).

**Layer 5 — Results and egress.** Opaque, per-result-set blank node labels (SQ-CONF-05). Hard result-size cap. Uniform error reporting that does not vary with hidden data or engine version (SQ-CONF-03, SQ-INJ-05). Mark non-deterministic queries uncacheable; include requester identity and effective dataset in every cache key (SQ-INT-01).

**Layer 6 — Observe.** Log the **algebra actually executed** and the **dereference targets actually resolved and contacted** — not the received text, which is the wrong artifact for exactly the reasons in SQ-INJ-03. Log `SILENT` failures server-side (SQ-NET-03). Treat query logs at the classification of the data they select over, with redaction and retention (SQ-CONF-07). Alert on query *shape* anomalies, which is the only practical detection for SQ-CONF-03 and SQ-CONF-08.

## 2. Mitigations by threat

One entry per threat, in catalogue order. Each entry names the threat it answers; the mechanism and impact are given in the [threat model](threat-model.md).

### 2.A Outbound requests — the service as a confused deputy

#### SQ-NET-01 — SSRF via `FROM` / `FROM NAMED`

- Do not dereference by default. Interpret `FROM`/`FROM NAMED` as *selection from the local store*. The spec permits this reading: the dataset description is "used in place of any dataset that the query service would use", and a service "may refuse a query request if the dataset description is not acceptable". Most mainstream engines already behave this way; it should be stated as the recommended default.
- Where dereference is wanted, allowlist IRIs or hosts, and decide policy on the **resolved IP address**, not the IRI string (see SQ-ID-02).
- Deny loopback, link-local (`169.254.0.0/16`, `fd00::/8`), RFC 1918, and multicast ranges; re-check **after every redirect**, and refuse cross-scheme redirects.
- Give the fetcher a distinct network identity and egress-proxy it; never let it inherit ambient cloud credentials.
- Cap per-fetch bytes, time, and total fetches per query.

#### SQ-NET-02 — Local file disclosure via `file:` and other schemes

Scheme allowlist (`http`, `https` only, if any). Run the engine as an unprivileged user with no readable secrets. Treat "dereference disabled" as the default. Note that disabling `file:` alone is insufficient — `http://localhost/` reaches a local server, and some URI stacks normalize unexpected schemes into file access.

#### SQ-NET-03 — SSRF *and bidirectional exfiltration* via `SERVICE`, including variable endpoints

- `SERVICE` disabled by default; enabled per-deployment with an explicit endpoint allowlist.
- **Enforce the allowlist at evaluation time, on the bound value**, not on the query text. Rejecting `SERVICE ?var` outright is the simplest sound rule and is what most locked-down deployments want.
- Never forward the service's own credentials to a federated endpoint; never let a variable-sourced endpoint inherit any credential.
- Egress-proxy and log the **resolved** endpoints actually contacted — not the query text.
- Log `SILENT` failures server-side even though they are hidden from the client.
- Treat a value drawn from the dataset as never acceptable as an endpoint (see SQ-INT-02).

#### SQ-NET-04 — Base IRI ambiguity relocates the dereference target

Require absolute IRIs for dataset and service references; reject relative ones there. Pin the base explicitly. For *policy* decisions (never for term identity, which must stay strict per RDF semantics), apply full RFC 3986 §6 normalization and resolve to an address before deciding.

#### SQ-NET-05 — Ingestion of attacker-controlled RDF

Byte and time caps per fetch; enforce `Content-Type` rather than sniffing; no cross-scheme or cross-host redirect following; parse under a memory cap. Treat any graph obtained by dereference as untrusted for downstream purposes, and label it as such in provenance.

### 2.B Availability — resource exhaustion

#### SQ-DOS-01 — Join and cross-product explosion

Bound intermediate cardinality, not just final result size — this is the one that matters, because `LIMIT` does not help (see SQ-DOS-03). Estimate cost before evaluating and refuse above a threshold. Cap the number of triple patterns and the join-graph's disconnected-component count. Hard wall-clock and memory limits per query, enforced by the executor rather than cooperatively.

#### SQ-DOS-02 — Property path explosion

A step budget inside `ALP`, checked per expansion and aborting the query rather than silently truncating (silent truncation returns *wrong answers*, which is worse). Cap closure-expression nesting depth. Require at least one bound endpoint for unbounded paths in hardened profiles. Convert recursion to an explicit worklist so traversal depth does not consume the call stack (see SQ-DOS-06).

#### SQ-DOS-03 — Sort, grouping, and aggregation memory

Spill to disk with a disk budget, or refuse. Cap group count, per-group accumulator size, and `GROUP_CONCAT` result length. Note explicitly in operator documentation that `LIMIT` is not a cost bound.

#### SQ-DOS-04 — String and numeric amplification

Cap literal length at parse time and intermediate string length at evaluation time, as hard errors. Cap digit count for numeric literals and bit-length for arbitrary-precision results. Clamp or reject `LIMIT`/`OFFSET` above a configured maximum; use a width that cannot overflow, and test the boundary.

#### SQ-DOS-05 — Regular-expression denial of service

Use a non-backtracking matcher (Thompson NFA / RE2-style) with linear-time guarantees — this is the only robust fix. Note the genuine tension worth flagging to the WG: back-references are not expressible in such engines, so a linear-time implementation may be unable to support the full `fn:matches` language. Failing that: per-call timeouts, pattern-length and nesting caps, compiled-pattern caching keyed on the pattern (so a constant pattern is compiled once), and refusal of data-sourced patterns.

#### SQ-DOS-06 — Parser and evaluator stack exhaustion from unbounded nesting

An explicit configured depth limit, returning a syntax error. Apply it in the parser *and* in every recursive walk over terms and algebra — comparison, ordering, hashing, serialization, and `CONSTRUCT` instantiation are each a separate recursion. Prefer an explicit stack to native recursion in the term walkers. A guard-page/stack-probe fallback is not sufficient on its own, since stack exhaustion in a shared process may be unrecoverable.

#### SQ-DOS-07 — Syntactic-sugar expansion defeats input-size limits

Apply size and depth limits to the **post-expansion AST or algebra**, not to the request body. Keep a request-body limit as well, but treat it as a coarse outer bound only.

#### SQ-DOS-08 — Correlated `EXISTS` / `NOT EXISTS` / `MINUS` cost

Cap `EXISTS` nesting depth. Account inner evaluations against the query's overall budget rather than treating each as fresh. Where an optimizing rewrite is used, ensure it preserves semantics. Short-circuit on first match, which the definition's "is not empty" permits.

#### SQ-DOS-09 — Amplification asymmetry (summary)

Because request count is a poor proxy for load, the budget must be denominated in work units — time, memory, intermediate cardinality — rather than requests.

### 2.C Injection and parsing integrity

#### SQ-INJ-01 — Query injection via string construction

1. **Do not build query text by concatenation.** Use a parameterized API that substitutes *RDF terms* into a pre-parsed query or algebra — `VALUES` or `BIND` of terms, not text.
2. If text must be built, escape with a library implementing [`#sec-escapes`](../../../spec/index.html#sec-escapes) exactly — and validate IRIs after resolution, not before.
3. Separate read-only and read-write endpoints with separate credentials; parse read endpoints at the `QueryUnit` entry point only.
4. Validate structurally, on the parsed form, not with text patterns or denylists.

#### SQ-INJ-02 — Grammar-entry-point confusion (read → write escalation)

Select the entry point from the protocol operation and the endpoint, never from the content. Reject anything that does not parse at the expected entry point. Enforce read-only at the *storage* layer too, so a mis-dispatch cannot write.

#### SQ-INJ-03 — Parser differentials desynchronize security controls

**Enforce policy on the translated algebra, inside the engine, after [`#translation`](../../../spec/index.html#translation)** — never on the text. Use one parser for both the control and the engine. Never re-serialize and re-parse a query between the control and the engine. Log the algebra actually executed and the dereference targets actually contacted, not the received text.

#### SQ-INJ-05 — `VERSION` is a client assertion, not a guarantee

Gate on what the parse actually contains, never on the declaration. Treat unknown labels consistently (prefer error). Keep error text uniform across versions.

### 2.D Confidentiality and inference

#### SQ-CONF-01 — The language defines no access-control model

Where dataset choice is a security boundary:

> **Set the dataset in the protocol request, and refuse queries that carry their own dataset description.** Both halves are explicitly permitted: the protocol override, and "A query service may refuse a query request if the dataset description is not acceptable to the service."

Beyond that: **the active dataset should contain exactly what the requester is permitted to see.** Authorize by *constructing the dataset*, not by filtering results — see SQ-CONF-03 for why the alternative fails.

#### SQ-CONF-02 — Metadata enumeration

Restrict the active dataset per requester so unauthorized names are not present (SQ-CONF-01). Do not encode sensitive information in graph IRIs — use opaque names with the sensitive mapping held separately. Treat graph-name enumeration as a privileged operation.

#### SQ-CONF-03 — Inference oracles: result-level filtering is not confidentiality

Authorize by restricting the **data**, before evaluation — dataset selection or pattern rewriting — so protected triples never enter the evaluation at all. If post-filtering is unavoidable, accept that it is a leak-rate reduction and not a confidentiality control: normalize error reporting, add per-identity rate limits and anomaly detection on query volume and shape, and log for after-the-fact detection. Note that timing mitigation in a query engine is impractical, which is itself an argument for the dataset-restriction approach.

#### SQ-CONF-04 — `DESCRIBE` is unbounded, implementation-defined disclosure

Disable `DESCRIBE` in access-controlled deployments, or implement it as an explicit, inspectable, ACL-respecting pattern with a hard size cap. **Do not implement it as "walk the store outward from this node."** Document the chosen description algorithm so deployers can reason about it.

#### SQ-CONF-05 — Blank node labels as a leak and a correlation handle

Emit opaque labels generated per result set, randomized or salted per result set. Never derive a label from a storage identifier, and never derive one deterministically from solution content. This deserves a note in [`#security`](../../../spec/index.html#security) — the scoping rules make it *permitted*, but nothing currently makes it *advised*.

#### SQ-CONF-06 — Hash functions: a guessing oracle, and two broken algorithms in the standard library

Treat an unsalted hash of a low-entropy identifier as **not** de-identification — this belongs in [`#privacy`](../../../spec/index.html#privacy), since it is the most common anonymization mistake in RDF data publishing. Document MD5 and SHA-1 as legacy and unsuitable for security purposes. Do not expose hash functions over values the requester cannot read (an instance of SQ-CONF-03's "filter the data, not the results").

#### SQ-CONF-07 — Query text is itself sensitive data

A [`#privacy`](../../../spec/index.html#privacy) item. Prefer POST for queries carrying identifiers; treat query logs at the data's classification; redact literals in logs where feasible while keeping the structure for debugging; set retention. Note the third-party disclosure inherent in dereference.

#### SQ-CONF-08 — Linkage, re-identification, and aggregate differencing

A [`#privacy`](../../../spec/index.html#privacy) item, and largely a governance one: query logging and review, minimum group sizes for aggregate release, suppression of small cells, and awareness that aggregate-only exposure is not a privacy control. For federation, control which endpoints may be contacted (SQ-NET-03) and record cross-domain flows.

### 2.E Extensibility

#### SQ-EXT-01 — Extension functions are arbitrary code in the evaluation path, named by the query

An explicit static registry; never resolve a function IRI dynamically; **never dereference a function IRI**. Treat registration as a privileged deployment-time action, not a runtime one. Apply the engine's resource caps and sandbox to extension code, and account its work against the query budget. Require each extension to document its own security considerations — the current [`#security`](../../../spec/index.html#security) sentence, "The SPARQL language permits extensions, which will have their own security implications", is correct but does not ask anything of anyone.

#### SQ-EXT-02 — Entailment regimes: unbounded cost, and inference around triple-level ACLs

Bound reasoning work and depth. Decide authorization over the **entailed** view, not the asserted one — or do not combine entailment with triple-level ACLs. Define behaviour on inconsistent input rather than leaving it to chance.

### 2.F Identity and naming confusion

#### SQ-ID-01 — IRI spoofing via confusables and bidirectional text

Compare allowlists on a normalized or Punycode form, never on display form. Apply confusable detection and script restriction in any tool that *displays* queries for review. Render IRIs so bidi reordering cannot mislead (isolate, or escape non-ASCII). Where a query is approved by a human, show the resolved and normalized targets separately from the source text.

#### SQ-ID-02 — No normalization: strict term identity, loose policy identity

Never use IRI string equality for an authorization decision; decide on the resolved network target, re-checked after redirects. Canonicalize at ingest so data has one spelling. Keep policy normalization strictly separate from term identity — normalizing terms would break RDF semantics.

#### SQ-ID-03 — Triple terms mention, they do not assert

Be explicit in application code and UI about mention versus assertion. Never treat a reifier's existence as evidence of truth, or its IRI as provenance, without an independent trust path (signature, trusted graph, verified source). Worth a note in [`#security`](../../../spec/index.html#security) given that this is new surface in 1.2 and that provenance is its primary use case.

### 2.G Integrity and non-determinism

#### SQ-INT-01 — Non-determinism breaks signing, caching, and audit replay

Do not sign or cache results of queries containing non-deterministic functions; detect them at parse time and mark the query uncacheable. Include requester identity and effective dataset in every cache key. Canonicalize (including blank node labels and ordering) before hashing. If a specific ordering matters, specify it fully in the query rather than relying on the partial order.

#### SQ-INT-02 — `RAND()` and `UUID()` are not security primitives, and data must not become control

State plainly that `RAND()`, `UUID()`, and `STRUUID()` are not cryptographic primitives and must not be used to generate secrets, tokens, or capability identifiers. Generate those outside the query with a CSPRNG and pass them in. Implementations should prefer UUIDv4 from a CSPRNG so that the common misuse fails safe.

A value drawn from the dataset must never be used as an endpoint, a pattern, or a function name without validation against a static allowlist. In hardened profiles, reject variable `SERVICE` endpoints outright. Keep ingest provenance so data-sourced values can be identified as such.

## 3. Residual risks and non-threats

### Accepted as inherent

| | Risk | Why it stays |
| --- | --- | --- |
| **RR1** | Query evaluation is computationally hard | Inherent in a pattern-matching language with `OPTIONAL` and paths. Manageable by limits ([R-1](threat-model-spec-actions.md)), not removable. |
| **RR2** | Timing side channels | Cost-based optimization and short-circuit evaluation make execution time data-dependent by construction. Only dataset restriction (layer 3) addresses it. |
| **RR3** | Expressiveness enables inference | A sufficiently expressive query language over a dataset permits inferences the publisher did not intend. Governance, not a language fix. |
| **RR4** | Implementation divergence in error cases | Explicitly licensed by [`#extensionFunctions`](../../../spec/index.html#extensionFunctions). Interoperability cost accepted; security controls must not depend on error behaviour. |
| **RR5** | Federation moves trust outside the deployment | Inherent in federation. Endpoint allowlisting bounds it; nothing eliminates it. |

### Explicitly *not* threats

Worth stating, to keep the model honest:

- **Reading public data from a public endpoint.** P1's data is public. Enumeration and bulk download are the service working as designed; only availability (A3) and the host's position (A4, A6) need defending.
- **A query being expensive.** Expensive is not malicious. The defence is a budget, not intent detection — which is also why cost heuristics should refuse rather than attempt attribution.
- **Blank node labels differing between runs.** Required latitude, not a bug ([`#BlankNodesInResults`](../../../spec/index.html#BlankNodesInResults)). The threat is labels that are *too stable*, not unstable ones.
- **`SERVICE` and `FROM` existing.** Federation and dataset-by-reference are features. The threat is unrestricted egress, not the constructs.
- **Non-total `ORDER BY`.** A deliberate design decision ([`#modOrderBy`](../../../spec/index.html#modOrderBy)). It becomes a problem only for consumers that assume byte-stable results.

## Appendix B — Implementer checklist

Parsing

- [ ] Configurable nesting-depth limit, enforced in the parser → SQ-DOS-06
- [ ] Depth limits in every recursive term walker: comparison, ordering, hashing, serialization, `CONSTRUCT` instantiation → SQ-DOS-06
- [ ] Size limits applied to the post-expansion AST/algebra, not the request body → SQ-DOS-07
- [ ] Escape processing during parsing, single-pass, no rescan; surrogates rejected → SQ-INJ-04
- [ ] Literal length and numeric digit-count caps at parse time → SQ-DOS-04
- [ ] `LIMIT`/`OFFSET` clamped; no integer overflow at the boundary → SQ-DOS-04

Evaluation

- [ ] Enforced wall-clock and memory limits; abort, never truncate → the threat model §3.B
- [ ] Intermediate cardinality bounded, not just final result size → SQ-DOS-01
- [ ] Property-path step budget inside `ALP` → SQ-DOS-02
- [ ] `EXISTS` inner evaluations accounted against the query budget; nesting capped → SQ-DOS-08
- [ ] Group count, accumulator size, and `GROUP_CONCAT` length capped → SQ-DOS-03
- [ ] Intermediate string length capped → SQ-DOS-04
- [ ] Arbitrary-precision numeric results bounded by bit-length → SQ-DOS-04
- [ ] Non-backtracking regex engine; pattern caps; compiled-pattern cache → SQ-DOS-05

Dereference and egress

- [ ] Dereference of `FROM`/`FROM NAMED` **off** by default → SQ-NET-01
- [ ] Scheme allowlist; `file:` excluded → SQ-NET-02
- [ ] Loopback, link-local, and private ranges denied; re-checked after each redirect; no cross-scheme redirects → SQ-NET-01
- [ ] `SERVICE` off by default; endpoint allowlist enforced **on the bound value at evaluation time** → SQ-NET-03
- [ ] Variable `SERVICE` endpoints rejected in the hardened profile → SQ-NET-03, SQ-INT-02
- [ ] No credential forwarding to federated endpoints → SQ-NET-03
- [ ] Per-fetch byte and time caps; `Content-Type` enforced, not sniffed → SQ-NET-05

Results and functions

- [ ] Blank node labels opaque, per result set; never from storage ids or solution content → SQ-CONF-05
- [ ] `UUID()` from a CSPRNG (prefer v4) so the common misuse fails safe → SQ-INT-02
- [ ] `DESCRIBE` implemented as an explicit, inspectable, size-capped pattern — not an open graph walk → SQ-CONF-04
- [ ] Error messages do not vary with hidden data or engine version → SQ-CONF-03, SQ-INJ-05
